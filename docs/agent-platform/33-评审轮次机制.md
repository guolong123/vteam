# 评审轮次机制

## 1. 背景与问题

`tm_0000000002` 计划评审时间线（2026-09-15 23:32 → 09-16 00:11，v0.1 → v0.4）：

* 测试一家 REJECT → 计划员**不等另两家**直接修订（m_446）；测试 APPROVE（m_455）→ 架构仍 REJECT（m_464）→ 计划员又并测试的非阻塞建议 → v0.4（m_465）；开发者二轮 REJECT 出新 findings（m_510）→ 再修订 v0.3（m_531）→ 三轮复评……
* PM 靠人肉数数维持秩序（“1/3”“2/3”“双 APPROVE 唯缺架构”m_433/440/497/549/553），依据是碰巧看到的消息；评审意见靠正文手写“212 行”“197 行”对版本，m_510（评 v0.3）与 m_498（评 v0.4）天然串味；测试/开发还撞了 S1 同一个阻塞（重复劳动）。

**根因一句话：评审只有散装 @，没有“轮次”对象——无期望人集合、无版本钉定、无收敛门，修订动作由最早到达的回执驱动。**

## 2. 目标与非目标

* 目标：每轮“谁评、评哪版、齐了没、改什么”全在账上；不到 N/N 计划员不得修订；过期回执自动作废不触发动作。
* 非目标：第一阶段不建新表（账本放 issue 内容 / 任务元数据 JSON，跑两轮验证后再定 schema）；不改变冷评审技能本身（只读、不改计划文件的纪律保留）。

## 3. 详细设计

### 3.1 轮次对象（ReviewRound，JSON 形态）

```json
{
  "round": 2,
  "planVersion": { "version": "v0.3", "lines": 233, "hash": "sha1前8" },
  "planPath": ".opencode/plans/alert-analyzer-fix-iteration-plan.md",
  "expected": ["tmm_0000000012", "tmm_0000000009", "tmm_0000000010"],
  "expectedRoles": ["架构视角", "开发视角", "测试视角"],
  "received": {
    "tmm_0000000010": { "verdict": "APPROVE", "msgId": "m_0000000540", "version": "v0.3" }
  },
  "status": "collecting",
  "timeoutAt": "2026-09-16T00:40:00Z"
}
```

* 存放：首轮放派发 issue 的内容区（机器可读段）+ PM 消息归档；第二阶段迁独立表/任务元字段。
* 版本钉定：`hash` 取计划文件落盘内容的 sha1 前 8（计划员修订落盘时由平台计算回填，不靠手写行数）。

### 3.2 派发词模板（强制三元组）

PM 派评审必须写清：`round + planVersion(+hash) + expected名单`，沿用 m_482/484/486 体例并追加三元组。缺三元组的派发视为无效派发（计划员有权退回）。

### 3.3 回执校验门（平台执行）

1. 缺版本号的 VERDICT → 打回（提示补版本），不计入 `received`。
2. 版本 ≠ 当前轮次版本 → 标 `superseded`（过期），**不触发修订**，仅归档备查。m_510 评 v0.3 而账本已到 v0.4 时自动走这条。
3. 同一轮次同一人多次回执 → 取最后一次（覆盖），不重复计数。

### 3.4 收敛门（核心）

* `received ⊇ expected`（人数齐；同一人多视角按 expected 条目计）→ 状态 `complete`，平台**自动**通知计划员“可修订”（`dispatchAgentMention` 带轮次摘要）并抄 PM。计划员在此之前按单份回执修订视为违规（m_446 类行为被拦）。
* 超时（默认 30 分钟，可配）未齐 → 状态 `stale`，转人工裁决：等 / 催办指定缺席人 / 降级放行（N-1 通过即放行，缺席视角记豁免），由老师或 PM 拍板，**不自动放行**。
* 修订落盘 → `version+1`、`round+1`，旧轮次整体归档（received 明细保留，可审计谁何时评了哪版）。

### 3.5 视角分工（治重复劳动）

派发词写死视角边界：架构只评方案/边界/状态机，开发只评可执行性/依赖/工作量，测试只评覆盖/判据可执行性。S1 式跨视角共识问题由 PM 在汇总时合并（去重），评审人不跨视角展开。

### 3.6 提示词补丁

* PM：派评审必须带三元组；未收敛不得通知修订；汇总格式固定（各视角 VERDICT + 共识阻塞 + 分歧点 + 待拍板项），即 m_553 体的规范化。
* 计划员：非 `complete` 轮次不得修订（老师明确 override 除外）；修订必须回填新 hash 并开新 round。
* 评审人：VERDICT 必须引用版本号；只读纪律不变。

## 4. 验收标准（用本次真实时间线重演）

1. m_446 不会发生：测试一家 REJECT 到达时门不开，计划员修订动作被拦并提示“待 2/3”。
2. m_510 与 m_498 分属 R2/R3，账本自动分开，不串味；过期回执标 `superseded`。
3. 三轮终态账本可导出：R1(3人)→修订v0.2→R2(3人)→修订v0.3→R3(开发+测试增量)→v0.4，每轮谁评了哪版可查。
4. 超时未齐转人工：有明确待拍板项，无自动放行。

## 5. 实施步骤

1. 轮次账本 JSON Schema + 存放约定（issue 内容机器段）+ 版本 hash 计算（计划员落盘时平台回填）。
2. PM 派发词模板（含三元组）+ 三方提示词补丁（seed）。
3. 收敛检查实现（先放 PM 侧流程函数/定时任务，不建表；`received==expected` 自动通知计划员）。
4. 超时转人工 + 豁免/降级路径。
5. 跑两轮真实评审验证后，评审是否建独立表（`review_rounds`）+ 15 篇落库。
6. 与 31/32 篇联调：修订通知走配对唤醒（31 篇），重复修订派发走在途锁（32 篇）。

## 6. 计划生命周期与用户放行门（评审后→执行前）

### 6.1 状态机（复活 `plans` 表，一任务一计划）

`plans.status` 复用既有枚举，映射用户要的五态（`reviewing/rejected` 归评审轮次 §3~§4 管）：

```
修订中(draft) → 待定稿(pending_final) → 已定稿待执行(approved) → 执行中(executing) → 执行完成(completed)
     ↑                 ↕ 用户定稿门        ↕ 用户确认门                  ↑                    ↑
     └── 评审 REJECT / 用户打回 ──┘   用户点[确认定稿]          用户点[确认开始]      PM 报完工/验收后
```

* 轮次全部 APPROVE → 状态置 `pending_final`（待定稿），**评审通过不等于定稿，不自动进入执行**。
* `pending_final → approved` 唯一入口：用户在页面点 [确认定稿]（或等效明确指令经 PM 落键，审计留痕 `finalizedBy/finalizedAt`）。
* `approved → executing` 唯一入口：用户在页面点 [确认开始执行]（或等效明确指令经 PM 落键，审计留痕 `confirmedBy/confirmedAt`）。
* `executing → completed`：PM 在执行交付齐后标记（MCP 工具 `vteam_plan_complete`；调用权由角色工具授权决定——`vteam-project_manager` 与 `vteam-plan` 的 `toolAllows` 持有该工具，服务端不按主实例身份判权；验收流程另行定义，不在本篇展开）。

### 6.2 执行门禁（机制，非自觉）

* 原「非 `executing` 拒绝派发」的**计划状态硬门禁已移除**：派发不再以 `plans.status='executing'` 为前提，服务端的状态拒绝分支与其「计划未放行」提示文案已删；计划状态仅用于页面徽标与流程提示，不再作为派发判定。
* **保留的唯一执行侧门禁是计划版本哈希**：调用方携带 `planHash` 且任务存在冻结哈希时比对，不一致即按 `plan-gated` 拦截并回「双短哈希」提示；该哈希门对**每个目标**生效（计划员目标 `agentId=a_plan` 的历史豁免已删除）。计划行兜底建行（`autoEnsureRow`）保留。
* 用户打回（`approved → draft`）：回填打回意见，轮次号不变、版本号 +1，重走收敛门。

### 6.3 页面（会话页计划 Tab）

* 状态徽标常驻：修订中（灰）/ 待定稿（琥珀闪）/ 已定稿待执行（琥珀闪）/ 执行中（蓝）/ 执行完成（绿），附版本号与轮次（`v0.4 · R3 · 3/3 APPROVE`）。
* `pending_final` 状态下同位置出现 [确认定稿] 主按钮（仅成员可见可点，二次确认防误触）；点击后状态翻 `approved`，群聊播一条系统消息。
* `approved` 状态下同位置出现 [确认开始执行] 主按钮（仅成员可见可点，二次确认防误触）；点击后状态翻 `executing`，群聊播一条系统消息，PM 自动续推 W2。
* `draft/reviewing` 显示当前轮次进度条（`received/expected` 名单，缺谁一目了然）；`executing` 显示执行项 checklist（读 issue 状态聚合，不另建账）。
* 完工由 PM 经 MCP 工具 `vteam_plan_complete` 触发（授权来自角色 `toolAllows`，不再按主 Agent 身份判定），页面徽标随 `plans.status` 自动更新，无需新增按钮。

### 6.4 定稿裁决增补（plan-finalize-actions todo 1 决策记录）

本节为 Wave 1 根决策，后续 todo 2/3 以此为准，只松不紧，不新增算法与门禁。

**裁决一：正式版双锚（dual-anchor）载体。**

* 正式版 = DB approved 行 + 文档版本哈希，双锚缺一不可：DB 行定状态与归属，文档哈希定内容。
* 哈希算法复用 triplet sha1-8（`review-round-ledger.ts` 既有 `planVersion.hash`，落盘内容 sha1 前 8），禁止引入新算法。
* 执行认哈希：门禁比对 `planVersion.hash`，不匹配即拦。

**裁决二：哈希计算钩（hash-compute hook）。**

* 钩位：计划员修订落盘后，读文件算 sha1 前 8，写回账本 `planVersion.hash`。
* 缺失语义：hash 缺失时到达的回执一律挂起，reason=`pending-hash`，不标 received，不标 superseded。
* 禁止悬空假设：不允许“某处自动算好”，接线点写死在 `writePlanDoc → applyRoundUpdate` 回填链。

**裁决三：修订入口矩阵（revise entry matrix）。**

| 当前状态 | 修订入口 | 动作 | version / 轮次规则 |
| --- | --- | --- | --- |
| approved | approved → draft 打回（带 reason） | 重走收敛门小循环 | version +1，轮次不变 |
| rejected | approved → draft 打回（带 reason） | 重走收敛门小循环 | version +1，轮次不变 |
| executing | 新增 revise 动作 | 回到 draft，version +1，轮次 +1，重走完整 N/N 复评 | 在途执行按门禁存量语义自然收敛，不追杀 |
| completed | 新增 revise 动作 | 回到 draft，version +1，轮次 +1，重走完整 N/N 复评 | 同上，不追杀已完成交付 |
| pending_final | 不可打回 | 只能等用户确认定稿或评审 REJECT | 不开修订入口 |

* 复评 quorum = N/N，沿收敛门。
* 打回必须带 reason，reason 落审计。

**force 口径：维持现状。**

* force 仍可绕过门禁，但须同时给非空 forceReason 留审计行（落回执行 forceReason 列），否则仍被拦。
* 不因哈希新增任何限制，不收紧现行放行面。

**C3 闭合门禁清单（逐项裁决只允许放宽或不动，收紧需单独立项）。**

* 执行门禁：计划状态硬门禁已移除；仅保留计划版本哈希校验（过期 `planHash` → `plan-gated`），只松不紧。
* issue 锁：issue 门禁未放行即拦（force + forceReason 可绕，留审计），只松不紧。
* 三元组门：回执三元组（member/verdict/msgId）缺一即拦，只松不紧。
* throttle：节流配额不动，不借定稿收紧。
* force：绕过留审计口径不变，不新增限制。
* a_plan 豁免：**已删除**——过期 `planHash` 对计划员目标（`agentId=a_plan`）同样拦截，哈希门对每个目标生效。
* toolAllows：plan 的 toolAllows 无记忆工具等约束不变，不借定稿扩权或收权。
* bash-edit：bash 编辑类约束不变，不借定稿收紧。
