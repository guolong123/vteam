## 2. 灰度开关

| 开关 | 默认 | 作用 |
|---|---|---|
| `SESSION_SCOPE` | `seat` | `member` 时启用「一成员一全局会话」；`seat` 完全保持旧行为 |
| `AUTO_PUSH`（既有） | 关闭 | 通知自动推送仍关闭，仅 `channel_send` 等显式发送 |

回滚：`SESSION_SCOPE` 改回 `seat` 并重启 server 即可；数据层为 expand 迁移，旧代码可继续运行。

## 3. 上线/联调顺序（MySQL）

```bash
cd server
npx prisma migrate deploy          # 应用 members + global_session 迁移
npm run backfill:members           # A) 席位 → 成员（1:1，幂等）
npm run backfill:member-sessions -- --dry-run
npm run backfill:member-sessions   # B) 席位会话 → 成员全局会话（认领最近一条）
SESSION_SCOPE=member <启动 server> # C) 灰度开启
```

验证点：
1. 建群时从成员库选人 → 群成员席位带 `member_id`；
2. 成员在 A 群被 @ 后，到 B 群再被 @：只有一条全局会话、上下文延续；
3. 成员库「状态」列显示处理中/空闲；
4. 私聊消息跨群聚合、已读一次清空；
5. 成员重置会话后下一轮新引擎会话，消息/记忆保留。

## 4. API 一览（新增/变更）

### 成员
- `GET/POST /members`、`GET/PATCH/DELETE /members/:id`
- `GET /members/:id/teams`、`POST /members/:id/clone`
- `POST /members/:id/reset-session`（成员级全局重置）
- `GET/PUT /members/:id/notification-channels`（独占绑定，409 可 `replaceExisting`）
- `GET /members/:id/messages`、`PATCH /members/:id/read`（P4 跨群私聊聚合）

### 会话
- `GET /conversations`（群聊 + 成员私聊平铺）
- `POST /dm-channels { memberId }`（成员维度，复用已有 DM）

### 任务通知（M8 下线）
- `GET/POST /tasks/:id/notification-channels` → `410 TASK_NOTIFICATION_BINDING_REMOVED`

## 5. 数据模型要点

- `members.member_key`：应用层列（`member_id`），仅有 team-mode 行非空；唯一索引 `uk_sessions_member`；
- `session_turns`：每轮冻结 `member/seat/team/channel/task/message`，`running_key` 唯一保证每会话至多一轮在飞；
- `chat_channels.member_id`：私聊归属成员（P0 迁移 + 回填）；
- `member_notification_channels`：成员渠道独占绑定（`notification_channel_id` 唯一）。

## 7. 已知限制 / 后续

1. **未做真实 MySQL + worker 端到端**：`SESSION_SCOPE=member` 的 enqueue→claim→execute→completed→drain 仅代码级/单测覆盖，需测试环境小流量验证；
2. **dispatcher member drain** 缺少专门单测（现状靠回归 + 代码审查）；
3. **DM 频道 `teamId`**：成员 DM 保留首次创建的团队上下文，跨群「最近上下文团队」未动态更新；
4. **旧私聊频道**：不清理、不搬消息，靠按成员聚合读兼容；如需收敛可再做清理脚本；
5. **`TaskNotificationChannel` 表**：端点已 410，表与清理逻辑暂留（expand/contract 的 contract 阶段再 drop）；
6. **成员合并**：P0 为 1:1 回填，同一真人多席位仍是多个成员，需要后续合并工具。
