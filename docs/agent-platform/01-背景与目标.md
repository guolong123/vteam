# 背景与目标

## 产品背景

以 opencode 为代表的 AI 编码工具，正在改变软件的开发方式。它们把大模型引入日常工程流，让开发者可以在会话里完成需求澄清、代码编写、错误排查等大量工作。

但这类工具的协作模式是"单会话持续沟通"。一个会话对应一个用户和一个 AI 助手，所有对话、推理与产出都挤在一条线性消息流里。当任务变复杂，需要需求、设计、开发、测试等多个角色参与时，问题就暴露出来了：

- **角色没有分工**。同一个 AI 助手既写需求又写代码又做测试，缺少角色边界，产出质量难以保证。
- **上下文难以组织**。需求、设计文档、代码、测试结论混在同一段对话里，消息越长，越难找到关键信息。
- **产出无法沉淀**。会话里的结论、文档、文件停留在聊天记录中，没有统一的归档位置，换一个任务就要重新沟通一遍。
- **协作缺少结构**。没有项目、任务、里程碑的概念，AI 参与的每一项工作彼此孤立，无法追溯"谁在什么阶段产出了什么"。

单会话模式适合"一个人问一个问题"，但不适合"一个团队做一个项目"。这正是本产品要解决的问题。

## 产品定位

本产品是基于 opencode 的多 Agent 协作控制平台。用户像组织项目团队一样组织 AI Agent：为任务挑选产品经理、架构师、开发者、测试等角色的 Agent，让它们在平台里分工协作，共同完成需求分析、设计、测试、开发与部署各阶段的工作。

产品把 AI 协作从"会话"升级为"项目制"：

- **任务即项目**。提交任务时选择多个 Agent，平台为任务建立专属的协作空间。
- **群聊即协作现场**。团队成员（人）和 Agent 在同一群聊中沟通，用 @ 显式触发指定 Agent 响应。
- **私聊即深度沟通**。用户可与单个 Agent 一对一讨论细节，不影响群聊节奏。
- **产出物即成果沉淀**。Agent 的结论文本、文档、文件统一归档为任务全局文档，带版本、可追溯、可复用。
- **Agent 配置即团队建设**。每个 Agent 可配置提示词、技能、工具与权限，像为团队成员定岗定责。

平台的技术底座是 opencode 的编程式驱动能力（opencode serve 与 SDK）：每个 Agent 对应一个独立的 AI 会话，由平台统一调度。技术细节不在本文展开，仅作为产品愿景的支撑前提。

群聊把「任务即项目」「群聊即协作现场」两条定位直观呈现出来，是本产品区别于单会话编码工具的核心形态。

## 产品目标

1. **让多角色 AI 协作结构化**。用户可为任务组建虚拟团队（产品/架构/开发/测试），角色分工明确，协作有固定流程而非依赖单一会话的临场发挥。
2. **让产出可归档、可追溯、可复用**。所有 Agent 产出物沉淀为任务全局文档，带版本历史；任务关闭后，文档、决策与过程依然可查，可作为后续任务的输入。
3. **让协作过程可控**。通过 @ 显式寻址与私聊，用户始终清楚哪个 Agent 在做什么；Agent 配置（提示词/技能/工具/权限）让团队行为可预期。
4. **让 AI 从"助手"变成"团队成员"**。用户面向任务的完整生命周期管理 Agent，而非在某个工具里零散地提问。

## 非目标

以下内容**不在本产品范围内**（第一版明确不做）：

- **不做模型训练与微调**。平台调度现成的大模型能力，不涉及模型本身的训练、微调或推理基础设施。
- **不做通用聊天工具**。平台是围绕"任务 + 项目制协作"的组织形态，不提供无任务、无产出的自由闲聊场景。
- **不替代 opencode 本身**。opencode 仍是底层 AI 工作引擎，平台在其之上提供多 Agent 协作的组织与控制层，二者是支撑与被支撑关系。
- **不做多租户 SaaS**（第一版）。平台先以团队内部署形态落地，多租户、计费、跨组织隔离等留待后续迭代。
- **不做 PR 合并与发布流水线**。PR 合并、CI/CD 部署等与代码托管平台强绑定的能力，属于后续迭代方向，不在第一版范围。
  - **平台产出代码文件在范围内**：开发者 Agent 生成的代码文件作为任务产出物归档进任务文档库（见 04 篇产出物协议），代码是任务的产出物，团队可查看、下载与追溯。
  - **仓库拉取/推送经本版凭证机制支持**（见 17 篇《仓库权限与凭证机制》）：分配给 Agent 的仓库可在权限申请（ask 确认）与临时凭证（短时效、用完即删）下执行 clone/pull/push；**PR 合并、CI/CD 部署、分支管理仍属后续迭代**。
  - **「开发阶段」的边界**：产品定位中的「开发阶段」指产出实现代码与实现说明，不包含将代码合并回仓库的流程。

## 目标用户

- **软件团队**：以产品经理、架构师、开发者、测试工程师为主要角色的项目团队。团队把部分分析、设计、开发与测试工作交给 AI Agent，需要一种能承载多人多角色协作的结构化方式。
- **使用 opencode 的工程师**：已经习惯用 opencode 驱动 AI 写代码的工程师，需要一个平台来组织多个 AI 角色并行工作、沉淀产出，而不是在多个会话间来回切换。
- **AI 工具的管理者与配置者**：负责为团队搭建 Agent（设定提示词、技能、工具与权限）的角色，他们关注 Agent 行为的可控性与产出质量的一致性。

这三类用户不是互斥的：一名开发者可能同时是 opencode 用户、虚拟团队的成员，也承担为团队配置 Agent 的职责。
