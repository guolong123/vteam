# 功能需求：任务与群聊协作

本文档将 02 篇的用户故事（US-01/02/03/06/07/08）转化为可落地的功能需求。每个功能点采用「FR-xx 编号 + 名称 + 描述 + 优先级」的形式；优先级 P0 表示第一版必须提供，P1 表示第一版应尽量提供，P2 表示后续迭代。

本文覆盖六个功能域：任务管理、群聊协作、消息上下文、实时性、用户与权限、Worker 节点与技能工具管理。Agent 配置与产出物管理的细节分别在 04 篇展开，此处仅涉及与任务群聊协作直接相关的部分。

## 1. 任务管理

任务是把 AI 协作组织起来的基本单元。成员提交任务、组建虚拟团队，并沿轻量的生命周期推进，直至验收归档。

### FR-01 任务创建

**优先级：P0**　**对应：US-01**

成员创建一个任务，需填写标题与描述，并可设置优先级（如高 / 中 / 低）；创建时还可上传任务背景文档（需求 / 资料等，支持多文件），作为任务背景资料进入任务文档库（见 FR-06）。任务创建后即生成任务群聊与任务文档库，作为该任务的协作空间与产出归档位置。

### FR-02 虚拟团队组建

**优先级：P0**　**对应：US-01**

创建任务时，成员从 Agent 角色列表中勾选一个或多个 Agent，组成该任务的「虚拟团队」。选中的 Agent 获得该任务的独立会话，未选中的 Agent 不参与本任务。团队组成在任务进行中可调整。

**进行中团队调整。** 任务启动后，团队组成仍可调整，规则如下：

- **添加 Agent**：新 Agent 加入时，平台将任务文档库内容注入其会话作为初始上下文（见 FR-15 上下文自动注入），使其快速掌握任务背景；加入后即可参与后续 @ 触发。
- **移除 Agent**：移除后该 Agent 不再接收本任务的 @ 与消息；其已提交的产出物保留在任务文档库中不删除；其会话归档 / 冻结，历史可查看，但不再处理新消息。
- **调整提示**：团队调整在任务群聊中以系统消息提示（见 FR-10 系统消息），成员可见谁加入、谁退出。

### FR-03 任务生命周期状态机

**优先级：P0**　**对应：US-06**

任务沿轻量状态机流转，共五个状态：

| 状态 | 含义 | 进入方式 |
|------|------|---------|
| 待开始 | 任务已创建、团队已组，等待人工触发开始（任务创建后的默认状态） | 任务创建后默认进入 |
| 进行中 | 已触发开始，Agent 协作中 | 成员点击「开始任务」触发（见 FR-07） |
| 待验收 | 产出已齐备，等待成员验收 | 成员在核对产出后手动标记（见 FR-04），Agent 不自动触发 |
| 已完成 | 验收通过，任务结项 | 成员在验收流程中确认通过 |
| 已归档 | 历史任务，仅供追溯 | 成员对已完成任务执行归档 |

状态变更在任务群聊中以系统消息提示，成员随时可见当前状态。

**本版边界：不支持删除 / 取消。** 本版任务不支持删除或取消，任务沿上述五态状态机流转直至归档，归档即为任务的终态（见 FR-05）；删除 / 撤回能力留待后续迭代。

### FR-04 验收流程

**优先级：P0**　**对应：US-06**

任务进入「待验收」后，成员核对任务文档库中的全部产出物（需求文档、设计文档、实现说明、验证结论等），确认符合预期后标记为「已完成」。验收未通过时，任务退回「进行中」继续协作，直至产出补齐后再进入「待验收」。验收结论由成员作出，Agent 不参与验收判定。

**进入待验收。** 任务从「进行中」进入「待验收」由成员手动标记，Agent 不自动触发。成员（通常为主验收人）在任务文档库中核对产出齐备后，主动将任务从「进行中」标记为「待验收」；手动判定比自动判定更可控，避免产出未齐备就提前进入待验收。进入待验收后按上述流程核对：通过则「已完成」，不通过则退回「进行中」。

**版本与验收联动。** 验收与产出物版本（见 04 篇 FR-43 版本历史）联动：

- **验收基线**：验收针对当前最新版本进行（如需求文档 v2），验收通过时记录该版本为「已验收版本」。
- **验收后更新**：已验收通过后，若 Agent 再次更新产出物生成新版本（如 v3），任务自动退回「进行中」，新版本需重新验收，确保验收针对最终交付。
- **已验收版本不可覆盖**：已验收版本（v2）不可被 Agent 修改或覆盖，Agent 只能在其后新增版本（v3），保证验收结论对应的内容不可变。

### FR-05 任务归档

**优先级：P1**　**对应：US-06**

已完成任务经团队确认不再跟进后，成员可将其归档。归档不删除任何内容，任务历史、群聊记录与全部产出物版本完整保留，可随时查阅与复用。

### FR-06 任务背景文档上传

**优先级：P0**　**对应：US-01（补充）**

创建任务时，成员可上传任务背景文档（需求说明、业务资料、数据样例等，支持一次上传多份），作为任务背景资料进入任务文档库。背景文档对任务内全部成员与参与 Agent 可见；@ 触发 Agent 时，背景文档随 FR-15 的上下文自动注入其会话，Agent 无需成员重复交代背景。

### FR-07 任务启动流程

**优先级：P0**　**对应：US-01（补充）**

任务创建后进入「待开始」，虚拟团队已组建但暂不投入协作。成员在任务看板或任务群聊中点击「开始任务」，人工触发任务启动：

- 启动前检查任务是否已选 Agent：未选择任何 Agent 时，弹出 Agent 选择面板，成员补选后再开始；已选择则直接开始。
- 多选 Agent 时，启动前须指定一个「主 Agent」作为任务负责人（见 FR-08）。
- 启动时平台向主 Agent 发送任务启动消息：任务群聊中以系统消息提示任务开始，并私信主 Agent 推送任务启动与背景资料，由主 Agent 牵头推进协作。
- 简单任务可仅选一个开发 Agent 承担，此时无需额外指定主 Agent（主 Agent 即该 Agent）。

任务启动后进入「进行中」，虚拟团队开始协作。

### FR-08 主 Agent 指定

**优先级：P0**　**对应：US-01（补充）**

组建虚拟团队且选择多个 Agent 时，成员须指定其中一个作为「主 Agent」，作为该任务的任务负责人。主 Agent 默认取产品经理 Agent（若其已选入团队，可改选其他已选 Agent），承担任务推进的牵头角色。主 Agent 的指定在任务启动时生效（见 FR-07）：任务开始后由主 Agent 接收启动消息、牵头各角色分工。仅选一个 Agent 的简单任务不需要额外指定主 Agent，该 Agent 即视为任务负责人。

**职责边界。** 主 Agent 的「主」体现在牵头协作，而非凌驾于团队之上：

- **协调权**：主 Agent 可 @ 其他 Agent 衔接协作（见 FR-13 Agent 间互 @），牵头各角色分工，推动环节衔接。
- **推进职责**：任务启动后接收启动消息（见 FR-07），向团队同步任务目标与分工；在环节间协调产出衔接，必要时向成员提示进度。
- **兜底设计**：主 Agent 无产出不阻塞任务，成员仍可直接 @ 各 Agent 推进；主 Agent 处理失败不视为整个任务失败（沿 FR-21 单 Agent 错误隔离，任务不因单个 Agent 失败而阻塞）。
- **不越权验收**：主 Agent 只是角色分工，牵头协作，不替代成员的验收判定权，验收结论仍由成员作出（见 FR-04）。

## 2. 群聊协作

每个任务有一个专属群聊，成员与虚拟团队的全部 Agent 在同一空间中协作。协作通过 @ 显式寻址触发，避免无关 Agent 被惊扰，也避免协作失控。

### FR-09 任务群聊

**优先级：P0**　**对应：US-01**

每个任务拥有一个专属群聊，任务成员与虚拟团队的全部 Agent 参与其中。群聊是任务协作的默认现场：发布需求、澄清问题、衔接环节都在群聊中进行。

### FR-10 消息模型

**优先级：P0**　**对应：US-02/03/07**

群聊中的消息分为三类：

| 消息类型 | 说明 | 示例 |
|---------|------|------|
| 用户消息 | 成员发出的消息，可携带 @ 触发 | 「@产品经理 请输出需求文档」 |
| Agent 回复 | 被 @ 的 Agent 处理完成后发出的最终回复 | 需求结论、设计要点、验证结果 |
| 系统消息 | 平台自动生成的状态与事件提示 | 任务进入待验收、产出物提交 |

三类消息在群聊中按时间顺序统一展示，成员可通过样式区分消息来源。

**消息内容类型（Part）**

一条消息在界面上由一个或多个内容片段（Part）组成。以下内容类型与展示规则是**基于 opencode 消息机制的技术愿景**，从产品视角描述，不涉及底层实现：

| 内容类型 | 产品呈现 | 展示规则 |
|---------|---------|---------|
| 正文（text） | 消息的主要文字内容 | 直接展示，是消息的主干；内部标记或占位性质的正文不展示 |
| 思考（reasoning） | Agent 的分析、规划过程 | 默认折叠，处理中显示「思考中…」，完成后可展开查看；不进入群聊（见 FR-18） |
| 工具调用（tool） | Agent 执行的操作，如读取文档、查询数据、生成产出物 | 以操作卡片展示，含进行中 / 完成 / 失败三种状态（失败见 FR-21 工具级错误） |
| 文件（file） | Agent 产出或引用的文件、产出物 | 以附件形式展示，可预览、下载，并进入任务文档库（见 04 篇产出物协议） |
| 中断（aborted） | 处理被主动停止的消息 | 显示「已中断」，明确区别于错误（见 FR-21） |

以下内容片段不直接渲染，仅作内部过程记录、按需查看或供会话上下文使用：内部步骤标记（step-start / step-finish）、补丁（patch）、快照（snapshot）、上下文压缩提示（compaction）。成员在群聊中只看到上述可展示类型，保持界面整洁（与 FR-18 内部过程不广播一致）。

### FR-11 定向 @ 触发

**优先级：P0**　**对应：US-02**

成员在群聊消息中 @ 指定 Agent 时，仅被 @ 的 Agent 收到并处理该消息，其他 Agent 不响应。这是显式寻址的核心约束：谁被 @，谁处理；未被 @ 的 Agent 保持静默，避免群聊消息引发无关 Agent 的连锁反应。

### FR-12 @all 广播

**优先级：P0**　**对应：US-02**

消息中 @all 时，消息广播给任务虚拟团队的全部 Agent，所有 Agent 均可响应。适用于需要团队全体知悉或参与的场合。

### FR-13 Agent 间互相 @

**优先级：P1**　**对应：US-02（补充）**

Agent 在回复中可以 @ 其他 Agent 以衔接协作，例如开发者 Agent @ 测试 Agent 提供可验证清单。被 @ 的 Agent 收到后在其自身会话中继续处理，与成员发起 @ 的机制一致。

**互 @ 循环控制。** Agent 互 @ 是衔接机制而非无限循环，平台对其加以约束，防止协作失控：

- **最大互 @ 轮次**：单个任务中 Agent 连续互 @ 的深度上限为 3 轮（A @ B → B @ C → C @ D 计 3 轮）；达到上限后平台停止自动衔接，并提示成员「协作轮次已达上限，请成员介入」。
- **循环检测**：同一对 Agent 连续互 @（A→B→A→B）超过阈值时，平台判定为疑似循环，中断衔接并提示成员，可能是任务目标不清或 Agent 卡在死循环。
- **成员介入**：成员可随时在群聊中插话或重新定向，通过 @ 指定 Agent 打破循环，重新明确任务目标后协作继续。

### FR-14 私聊与群聊共用会话

**优先级：P0**　**对应：US-03**

平台为每名 Agent 的每个任务维护一个独立会话（session）。成员与 Agent 的私聊、群聊中 @ 该 Agent，共用同一个会话，上下文连续。成员可私聊深入讨论细节而不在群聊刷屏，Agent 始终记得任务上下文，不会因入口不同而失忆。

## 3. 消息上下文

Agent 被 @ 触发时需要足够的上文才能高质量作答。平台自动注入上下文，减少成员重复交代背景。

### FR-15 上下文自动注入

**优先级：P0**　**对应：US-08**

@ 触发 Agent 时，平台自动把以下内容注入其会话上下文：

- 任务群聊的历史消息（该任务下此前的对话记录）
- 任务文档库内容（需求文档、设计文档、实现说明等全部产出物及其版本）

Agent 据此基于任务最新状态作答，成员无需重复背景信息。

### FR-16 上下文分层管理（后续迭代）

**优先级：P2**　**对应：US-08（延伸）**

第一版通过注入最新群聊历史与文档库保证上下文质量。当任务历史变长、文档增多导致 token 开销增大时，引入上下文 token 的分层管理策略（如按相关性裁剪、分轮整理注入等），作为后续迭代方向，不在第一版范围。

## 4. 实时性

Agent 处理需要时间。平台让处理过程可见但不打扰：Agent 处理期间以 Loading 状态提示进展（FR-20），异常时以消息形式反馈（FR-21）；内部过程不广播到群聊，群聊只显示最终回复；成员可点击 Agent 实时查看其会话过程。

### FR-17 实时查看 Agent 会话

**优先级：P0**　**对应：US-07**

成员点击群聊或私聊中的 Agent，可实时查看该 Agent 当前会话的处理过程，包括思考与操作进展。查看是单向的观察行为，不打断 Agent 正在进行的处理。

### FR-18 内部过程不广播

**优先级：P0**　**对应：US-07**

Agent 的内部思考与操作过程不广播到群聊，群聊中只显示其处理完成的最终回复，保持群聊整洁。内部过程的展示仅发生在成员主动点击查看时。

### FR-19 群聊消息持久化

**优先级：P0**　**对应：US-08**

任务群聊的全部消息在平台内持久保存，作为任务历史的一部分。持久化的消息既是 FR-15 上下文注入的来源，也支撑任务归档后的历史追溯，确保协作过程可回看、可复用。

**本版边界：不支持撤回 / 编辑。** 本版消息不支持撤回或编辑，误发消息无法撤销，可重新发送以纠正。

### FR-20 Agent 处理 Loading 状态

**优先级：P0**　**对应：US-07**

Agent 收到 @ 后进入处理中状态，界面以 Loading 指示器呈现其处理进展，让成员明确知道 Agent 正在工作。Loading 状态展示于：

- 群聊中该 Agent 的消息气泡区域：处理中显示「思考中… / 操作中…」指示器，处理完成后替换为最终回复；
- 成员面板与私聊：Agent 状态展示为「处理中」，与「空闲 / 在线」区分。

Loading 呈现两个阶段，对应 Agent 处理的不同环节：

| 阶段 | 指示器 | 说明 |
|------|--------|------|
| 思考中 | 「思考中…」 | Agent 正在分析问题、规划方案，对应消息内容类型中的思考片段进行中（见 FR-10） |
| 操作中 | 「操作中…」 | Agent 正在执行工具操作（读取文档、查询数据、生成产出物），对应工具调用片段进行中 |

思考与操作的详细过程不进入群聊气泡（FR-18 内部过程不广播的约束不变），群聊仅显示阶段性指示器；成员点击该 Agent 可实时查看完整过程（FR-17）。处理完成后 Loading 指示器消失，其最终回复显示于群聊。

以上 Loading 语义是**基于 opencode 消息机制的技术愿景**：处理中对应底层会话的忙碌状态，思考指示器对应思考片段进行中，操作指示器对应工具调用片段进行中；产品侧仅呈现「思考中 / 操作中」两个阶段的轻量指示，不暴露过程细节。

### FR-21 Agent 错误反馈

**优先级：P0**　**对应：US-07（补充）**

Agent 处理过程中发生异常时，错误信息以消息形式返回显示，而不是静默失败。错误消息在任务群聊与私聊中均可见，成员据此知晓处理失败的原因。任务不因单个 Agent 失败而阻塞，成员可重新 @ 触发重试；连续失败时，错误消息提示成员检查该 Agent 的配置或稍后再试。

错误反馈按三层模型呈现（**基于 opencode 消息机制的技术愿景**，产品视角描述）：

**第一层：工具级错误。** Agent 执行某个工具操作失败时，在该操作的卡片内直接显示失败原因（如「读取文档失败」），Agent 可在后续步骤中自动重试或换一种方式完成，通常无需成员介入。

**第二层：消息级错误。** 整条 Agent 回复失败时，以错误消息形式呈现，共八种，均显示失败原因并提示处理方式：

| 错误类型 | 含义 | 展示方式 | 是否可重试 |
|---------|------|---------|-----------|
| 认证失败 | Agent 的凭据无效或过期 | 错误消息提示重新配置凭据 | 否，需成员处理 |
| 模型服务错误 | 底层模型服务异常（模型繁忙 / 限流 / 超时 / 余额不足） | 错误消息显示具体原因 | 视场景而定，见下方映射表 |
| 输出超长 | 回复内容超过长度限制 | 错误消息提示分步提问或精简输出 | 否，需成员处理后重试 |
| 用户中断 | 成员主动停止处理 | 显示「已中断」，区别于错误 | 否，不重试 |
| 结构化失败 | 结构化输出未通过校验 | 错误消息提示重试 | 是，可自动重试 |
| 上下文超限 | 会话上下文超出限制 | 错误消息提示精简上下文或分轮提问 | 否，需成员处理后重试 |
| 内容过滤 | 输出被内容安全策略拦截 | 错误消息提示调整请求内容 | 否，需成员处理后重试 |
| 未知错误 | 未识别的异常 | 错误消息提示稍后再试或检查配置 | 是，可重试 |

**第三层：重试级反馈。** 自动重试时，界面显示重试次数与等待时间（如「模型繁忙，将在 30 秒后自动重试（第 2 次）」）；重试多次仍失败后，转为消息级错误提示成员手动处理。

常见场景映射：

| 场景 | 错误表现 | 平台行为 | 成员视角 |
|------|---------|---------|---------|
| 模型繁忙 | 消息级「模型服务错误」 | 自动重试（含次数与等待时间），多次失败后转为错误消息 | 看到重试提示；仍失败则重新 @ 触发 |
| 限流 | 消息级「模型服务错误」 | 按提示的等待时间自动重试 | 看到重试倒计时 |
| 超时 | 消息级「模型服务错误」 | 自动重试 | 看到重试提示 |
| 余额不足 | 消息级「模型服务错误」 | 不自动重试 | 提示补充额度后重试 |
| 用户中断 | 「已中断」提示 | 立即停止，不作错误处理 | 看到「已中断」，与错误明确区分 |

其中，模型繁忙 / 限流 / 超时属于可自动重试的临时性问题；余额不足与认证失败属于需成员处理的问题（补充额度、重新配置）；用户中断不视为错误，不进入错误计数，也不触发重试。

## 5. 用户与权限

平台权限回答「用户能操作什么」：平台管理员维护账号与角色，通过权限矩阵与权限范围控制每类角色对平台资源的操作能力。该域由平台管理员使用，与成员侧的任务群聊协作相互独立。

### FR-22 用户管理

**优先级：P0**　**对应：US-13**

平台管理员对平台用户进行全生命周期管理：

- **新增用户**：创建平台账号，填写用户名、邮箱与初始密码，并分配角色（管理员 / 成员）与所属项目（可多选）。
- **编辑用户**：修改用户的基础信息、角色与所属项目归属。
- **禁用 / 启用用户**：禁用后用户无法登录与操作，启用后恢复；禁用不删除账号数据。
- **重置密码**：为忘记密码或需要变更凭据的用户重置密码，重置后用户以新凭据登录。

账号体系为平台内置，用户归属项目，在项目内以成员身份参与任务（与 02 篇 1.1 / 1.2 一致）。

### FR-23 角色权限矩阵

**优先级：P0**　**对应：US-14**

平台管理员通过「资源 × 操作」矩阵配置每类角色能对平台资源执行的操作，控制用户能操作什么：

| 维度 | 内容 |
|------|------|
| 资源（行） | 任务 / 群聊 / 产出物 / Agent 配置 / Worker 节点 / 技能工具 / 用户管理 / 权限配置（对齐平台业务域） |
| 操作（列） | 查看 / 创建 / 编辑 / 删除 / 验收 / 管理 |
| 矩阵格值 | ✓ 允许 / ◐ 部分允许 / ✗ 禁止 |

角色分为预置角色（平台管理员、项目成员）与自定义角色：平台管理员默认全资源允许；项目成员在所属项目内具备任务协作权限，但对用户管理、权限配置等管理资源禁止；自定义角色按需组合，如「验收员」「运维专员」等岗位化角色。

「技能工具」资源行含**工具级权限**：每个工具是一个独立的权限点（action），矩阵按工具粒度给出角色对该工具的整体允许 / 部分允许 / 禁止。工具内部的执行策略（每次执行是否确认）不属于平台权限矩阵，由 Agent 侧工具权限逐工具配置（effect 取值 allow / ask / deny，支持通配符批量授权，见 04 篇 FR-48）。

**删除操作适用范围**：矩阵中的「删除」为通用操作模板，仅作用于本版可删除的对象（如项目成员移除、自定义角色删除）；对任务、消息、产出物等本版不可删除的资源（见 FR-03 / FR-19 / 04 篇 FR-43），删除操作一律为 ✗ 禁止。

### FR-24 权限范围

**优先级：P0**　**对应：US-14**

角色权限按范围生效，控制该角色的权限覆盖哪些项目：

- **全局（所有项目）**：角色权限对所有项目生效，如平台管理员。
- **指定项目（多选）**：角色仅对所选项目生效，如项目成员。
- **项目内角色**：成员在项目内可承担多种分工（产品经理 / 架构师 / 开发者 / 测试 / 验收），权限按分工细分。

### FR-25 项目生命周期

**优先级：P0**　**对应：US-15**

项目是任务与成员的归属边界，平台采用「仅项目」组织模型，不设组织层级：

- **项目创建**：平台管理员（或获得授权的成员）创建项目，填写名称与描述；项目创建后即成为任务与成员归属的边界。
- **成员管理**：平台管理员将用户加入 / 移出项目；用户加入项目后，可在该项目内创建任务、参与任务群聊协作。
- **项目内权限**：项目成员在项目内按角色分工协作（产品 / 架构 / 开发 / 测试），具体操作能力由角色权限矩阵与权限范围约束（见 FR-23 / FR-24）。

**与现有 FR 衔接**：任务属于项目，FR-01 任务创建在项目内进行；用户管理（FR-22）为用户分配所属项目；权限范围（FR-24）的「指定项目」维度即按项目边界生效。

### 平台权限与 opencode 权限的边界

平台权限与 opencode 权限**相互独立、互不干扰**：

- **平台权限**管「用户能操作什么」：用户在控制面创建任务、查看产出物、管理账号与配置权限的能力，由本页（FR-22 / FR-23 / FR-24）约束。
- **opencode 权限**管「agent 能做什么」：Agent 运行时可用的工具 / 文件 / 命令边界，经 PermissionV2 Ruleset 下发（详见 04 篇与 07 篇）。

即使用户被授予全部平台权限，agent 的能力边界仍由 opencode 权限单独约束；反之，提升 agent 权限也不会扩大用户在控制面的操作范围。

## 6. Worker 节点与技能工具管理

Agent 的实际运行需要计算资源与能力来源。平台通过 Worker 节点池承载 opencode 运行时与任务组实例，通过技能库与工具注册为 Agent 提供可勾选的能力（技能见 FR-34，工具权限见 04 篇 FR-35 / FR-48）。本功能域是平台管理侧的能力，由平台管理员维护，与成员侧的任务协作相互独立。

### FR-26 Worker 节点管理

**优先级：P0**　**对应：US-14（补充）**

Worker 是承载 opencode 运行时与任务组实例的数据面节点，平台控制面通过 Worker 节点池调度 Agent 的实际运行（架构蓝图对齐 07 篇第 11 章分布式 Worker）：

- **注册与心跳**：Worker 启动后主动向控制面注册，上报 workerId、opencode 版本、能力声明（支持的版本、并发上限、可用 skill/tool 清单）、负载与健康状态；注册成功后周期性上报心跳，连续超时 N 个周期标记离线，其任务组进入待重调度。
- **生命周期管理**：支持主动启停与崩溃自愈。优雅停止先收口进行中的会话再退出，强制终止直接杀进程；离线 / 崩溃后调度器按亲和与负载策略将任务组迁移到存活节点。
- **任务调度**：任务组绑定 Worker 上的 opencode 实例运行（每任务组一个实例，见 07 篇第 9 / 10 章），调度器按能力与负载选择节点；水平扩容即加即用，新 Worker 注册即入池。
- **运维可见**：平台提供 Worker 列表，展示节点状态（在线 / 离线）、负载、能力与 opencode 版本，供调度与运维查看；该资源行已纳入角色权限矩阵（见 FR-23）。

### FR-27 技能与工具管理

**优先级：P0**　**对应：US-05（延伸）**

平台统一管理 Agent 可用的技能与工具，作为 Agent 配置（FR-34 技能、04 篇 FR-35 / FR-48 工具）的能力来源：

- **技能管理**：技能以上传方式进入平台技能库（如 SKILL.md 技能包），可启用 / 停用；启用的技能可供 Agent 勾选（见 FR-34），随上下文注入 Agent 会话。
- **工具注册**：支持注册自定义工具，注册时声明工具名（即权限 action，见 04 篇 FR-48）与执行方式。执行方式支持四种：**代码**（内嵌脚本）、**CLI**（命令行调用，可配置初始化命令）、**HTTP**（远程接口调用）、**MCP**（经 MCP 接入的外部工具，权限点形如 `<server>_<tool>`）。
- **初始化命令**：CLI 等执行方式可配置初始化命令，工具首次加载时执行，用于准备运行环境。
- **注册生效**：工具注册后自动进入权限命名空间（工具名即 action，见 04 篇 FR-48），并可在 Agent 配置页逐工具配置 effect（见 04 篇 FR-35 / FR-48）；「技能工具」资源行已纳入角色权限矩阵（见 FR-23）。
