# 用户与场景

本文档定义 Agent 协作平台的用户角色、核心用户故事与典型使用场景，是后续功能需求章节（03/04 篇）的用户侧依据。所有故事与场景均严格基于已确认的需求：任务群聊 + @触发、每 Agent 每任务一个会话（群聊 @ 与私聊共用）、产出物归档为任务全局文档、Agent 角色模板与自定义、轻量任务状态机。

## 1. 用户角色

平台采用「仅项目」的组织模型：用户归属项目，在项目内以成员身份参与任务。账号体系为平台内置。

### 1.1 平台管理员

- 管理平台账号与项目生命周期（创建、成员维护、停用）
- 维护 Agent 角色模板库（预置模板的增改与发布）
- 制定全局安全与权限策略，处理权限请求

### 1.2 项目成员

项目成员即实际使用平台的软件团队成员，典型分工如下：

| 角色 | 主要职责 | 在平台中的典型行为 |
|------|---------|-------------------|
| 产品经理 | 需求分析、验收 | 提交任务、在群聊中 @ 产品经理 Agent 输出需求文档、验收产出 |
| 架构师 | 技术设计 | @ 架构师 Agent 产出技术方案与设计文档 |
| 开发者 | 功能实现 | @ 开发者 Agent 产出代码与实现说明 |
| 测试 | 质量验证 | @ 测试 Agent 产出测试用例与验证结论 |
| 验收 | 产出核对与验收判定 | 核对产出物，将任务手动标记为待验收 / 已完成 |

一名成员可同时承担多个分工；成员不是 Agent 的替代，而是任务的发起者、协作的参与者与最终验收者。

### 1.3 AI Agent 角色列表

平台预置以下 Agent 角色模板，成员可在此基础上克隆修改或完全自定义：

| Agent 角色 | 定位 | 典型产出物 |
|-----------|------|-----------|
| 产品经理 Agent | 需求拆解与文档化 | 需求文档、验收标准 |
| 架构师 Agent | 技术方案与设计 | 设计文档、方案对比结论 |
| 开发者 Agent | 代码实现与说明 | 实现文档、代码文件 |
| 测试 Agent | 用例设计与验证 | 测试用例、验证结论 |
| 自定义 Agent | 成员按需创建 | 按配置决定 |

每个 Agent 都是独立的会话个体：平台为每名 Agent 的每个任务维护一个独立会话（session），群聊中 @ 触发与私聊共用该会话；Agent 的提示词、技能、工具与权限范围均可配置（详见 04 篇）。

### 1.4 用户与权限模型

平台权限回答「用户能操作什么」：平台管理员通过用户管理维护账号（新增 / 编辑 / 禁用 / 重置密码 / 分配角色），通过角色权限配置控制每类角色对平台资源的操作能力（资源 × 操作矩阵）与权限范围（全局 / 指定项目 / 项目内角色）。用户被分配的权限决定其在控制面能创建任务、查看产出物、管理账号与配置权限等。

平台权限与 opencode 权限**相互独立**：opencode 权限回答「agent 能做什么」，约束 Agent 运行时可用的工具 / 文件 / 命令边界（经 PermissionV2 Ruleset 下发）。两条链路独立配置、互不干扰：即使用户被授予全部平台权限，agent 的能力边界仍由 opencode 权限单独约束。

### 1.5 三种角色的关系

平台中存在三套并行但互补的角色概念：

- **平台角色**（管理员 / 成员）：决定用户在平台的整体权限，覆盖用户管理、权限配置等管理域，回答「能否进入平台、能否管理平台」。
- **项目内分工**（产品 / 架构 / 开发 / 测试 / 验收）：成员在项目内承担的业务职责，决定其在项目里 @ 哪个 Agent、承担哪类产出与验收，回答「在项目里干什么」。
- **自定义角色**（验收员 / 运维专员）：平台管理员按岗位组合的权限配置，可覆盖项目内分工场景，是平台角色与项目内分工的组合扩展。

三者关系：平台角色管「能否进平台 / 管理域」；项目内分工管「项目里干什么」；自定义角色把平台角色与分工按岗位组合，实现更细粒度的授权（具体配置见 03 篇 FR-23 权限矩阵与 FR-24 权限范围）。

## 2. 核心用户故事

> 以下故事均采用标准格式，覆盖已确认需求的六个方面与任务管理增强项（文档上传、待开始、处理中 Loading 与错误反馈、默认模型），并补充实时查看会话与上下文注入、用户管理与权限控制等衍生故事。

**US-01 组建虚拟团队**

> As a 项目成员,
> I want to 提交任务时从 Agent 角色列表中选择多个 Agent 组成「虚拟团队」,
> So that 一个任务可以由多个角色分工协作完成，而不必我逐个单独驱动。

**US-02 群聊 @ 触发**

> As a 项目成员,
> I want to 在任务群聊中 @ 指定的 Agent，且只有被 @ 的 Agent 收到该消息,
> So that 我可以明确寻址，避免无关 Agent 被惊扰，也避免协作失控。

补充：Agent 之间也可以互相 @ 以衔接协作；支持 @all 广播给团队全部 Agent。

**US-03 私聊讨论细节**

> As a 项目成员,
> I want to 与单个 Agent 私聊讨论细节，并保持与群聊 @ 时同一会话的上下文连续性,
> So that 我不必在群聊里刷屏即可深入沟通，Agent 也始终记得任务上下文。

**US-04 查看产出物**

> As a 项目成员,
> I want to 查看 Agent 提交的产出物（结论文本、文档、文件），它们作为任务的全局文档对团队所有成员与所有 Agent 可见,
> So that 任务的成果有唯一权威载体，各环节可以直接衔接复用，而不依赖对话记录。

产出物带版本历史：更新产出会生成新版本，团队成员可追溯每次变更。

**US-05 配置 Agent**

> As a 项目管理员或项目成员,
> I want to 配置 Agent 的提示词、技能、工具与权限范围，并支持从预置模板克隆后修改或完全自定义,
> So that 我可以让 Agent 的行为贴合项目规范与个人工作方式。

**US-06 验收与归档**

> As a 项目成员,
> I want to 在 Agent 产出完成后对任务进行验收，确认通过后任务进入已完成，并可将历史任务归档,
> So that 任务生命周期清晰可控（待开始 / 进行中 / 待验收 / 已完成 / 已归档，五状态），团队可以区分活跃与结项工作。

**US-07 实时查看 Agent 会话**

> As a 项目成员,
> I want to 点击群聊或私聊中的 Agent，实时查看其会话处理过程,
> So that 我能了解 Agent 的思考与操作进展；同时 Agent 的内部过程不广播到群聊，群聊只显示最终回复，保持群聊整洁。

**US-08 上下文注入**

> As a 项目成员,
> I want to 在 @ 触发 Agent 时，平台自动把群聊历史与任务文档库内容注入其会话上下文,
> So that Agent 无需我重复背景信息即可基于任务最新状态作答。

**US-09 上传任务背景文档**

> As a 项目成员,
> I want to 创建任务时上传背景资料（需求说明、参考文档等），作为任务文档存入任务文档库供任务内 Agent 查看,
> So that Agent 开始处理前就能掌握完整背景，减少重复澄清。

**US-10 待开始与人工启动**

> As a 项目成员,
> I want to 任务创建后先处于「待开始」，由我确认 Agent 团队后再手动触发开始；未选择 Agent 时先完成选择，多 Agent 时指定一名主 Agent 作为负责人,
> So that 任务在团队与背景资料齐备后才启动，Agent 不会过早开工，任务也有明确的负责人。

补充：未选择 Agent 时任务停留在「待开始」并提示先完成选择；简单任务可只选一名开发 Agent 直接开工，无需主 Agent；多 Agent 协作时主 Agent 通常由产品经理/项目经理 Agent 担任，启动后消息优先发送给主 Agent。

**US-11 查看处理中状态与错误反馈**

> As a 项目成员,
> I want to 在 Agent 处理时看到 Loading 状态，并在 Agent 异常（模型繁忙、余额不足、超时）时收到错误反馈、可点击重试,
> So that 我能了解处理进展与失败原因，任务停滞时能及时重试，而不是干等或猜测。

**US-12 配置默认模型**

> As a 项目成员,
> I want to 创建或编辑 Agent 时为其设置默认模型，模型列表来自 opencode,
> So that 我能按成本与效果为不同 Agent 指定合适的模型，触发时无需每次单独指定。

**US-13 用户管理**

> As a 平台管理员,
> I want to 管理平台用户（新增、编辑、禁用、重置密码），并为用户分配角色（管理员 / 成员）与所属项目,
> So that 平台账号体系可控，用户以正确的角色与归属进入对应项目协作。

**US-14 权限控制**

> As a 平台管理员,
> I want to 配置角色权限（资源 × 操作矩阵）与权限范围（全局 / 指定项目 / 项目内角色），控制用户能操作什么,
> So that 不同角色各司其职，越权操作被平台权限拦截；平台权限与 opencode 权限独立，agent 的能力边界不受平台授权影响。

**US-15 项目生命周期**

> As a 平台管理员或项目成员,
> I want to 创建项目并将成员加入项目,
> So that 用户在项目内协作有边界，任务归属明确。

## 3. 典型使用场景：新功能开发

本场景演示一次完整的端到端协作：产品经理出需求 → 架构师设计 → 开发者实现 → 测试验证，各环节通过群聊协作与产出物衔接。团队为「智能报表模块」开发成员：产品经理小陈、架构师小张、开发者小王、测试小李。

### 步骤 1：提交任务，组建虚拟团队

小陈进入平台，创建一个新任务「智能报表模块」，填写描述与优先级，并上传需求文档作为任务背景资料，存入任务文档库供 Agent 查看。在 Agent 选择区勾选产品经理、架构师、开发者、测试四名 Agent，组成虚拟团队。任务创建后处于「待开始」，群聊与文档库随即就绪，四名 Agent 各获得一个独立会话，等待成员确认启动。

小陈在任务创建页完成上述操作，界面效果见下方原型预览：

```prototype
id: task-create
title: 任务创建-组建虚拟团队
device: desktop
height: 720
```

创建成功后任务处于「待开始」状态；小陈确认 Agent 团队并触发开始后（见步骤 1.5），任务进入「进行中」，进入后续协作环节。

### 步骤 1.5：确认 Agent 团队，触发开始

任务创建完成后停留在「待开始」。小陈在任务详情页核对任务信息：需求文档已上传至文档库，产品经理、架构师、开发者、测试四名 Agent 已组成虚拟团队。由于本任务由多名 Agent 协作，小陈指定产品经理 Agent 为主 Agent（负责人），对任务整体负责并衔接各环节；若为简单任务，可只选一名开发 Agent，则无需主 Agent。

确认无误后，小陈点击「开始任务」，任务进入「进行中」，平台将启动消息发送给主 Agent；主 Agent 向团队同步任务目标与分工，协作正式展开。

### 步骤 2：产品经理出需求

小陈在群聊中发送消息：

> @产品经理 请为「智能报表模块」输出需求文档，包含报表类型、字段与验收标准。

只有产品经理 Agent 收到该消息，进入处理中状态，群聊中显示 Loading 提示，小陈可点击 Agent 实时查看处理过程。首次调用时模型繁忙，处理失败，群聊中收到错误反馈（「模型繁忙，请重试」）；小陈点击重试，产品经理 Agent 重新开始处理，在会话中分析任务描述与已注入的任务文档库内容（含步骤 1 上传的需求文档），内部完成需求拆解后，向群聊回复最终结论，并将「需求文档」作为产出物提交到任务文档库（版本 v1）。

小陈 @ 产品经理的群聊协作场景见下方原型预览：

```prototype
id: group-chat
title: 任务群聊（@ 触发协作）
device: desktop
height: 720
```

群聊中仅被 @ 的 Agent 收到消息并回复，其余 Agent 保持静默，协作现场整洁可控。

### 步骤 3：架构师设计

架构师 Agent 在群聊中 @ 产品经理 Agent：

> @产品经理 报表的数据源与刷新频率约束是什么？

产品经理 Agent 据此补充需求，更新需求文档为 v2。随后架构师 Agent 输出「技术方案设计文档」并提交为产出物，说明模块划分与实现路径。

### 步骤 4：开发者实现

开发者 Agent 读取文档库中的需求文档与设计文档（@ 触发时自动注入），开始实现。它将实现说明作为产出物提交，同时上传关键代码文件。小陈无需守在群聊旁，点击开发者 Agent 即可实时查看其会话处理过程；群聊里始终只出现各 Agent 的最终回复。

### 步骤 5：测试验证

测试 Agent @ 开发者 Agent：

> @开发者 实现已就绪，请给出可验证的接口清单。

随后测试 Agent 基于需求文档中的验收标准产出「测试用例与验证结论」，标注发现的待确认问题。小陈在群聊中看到结论后，@ 开发者 Agent 跟进修复，实现说明更新为 v2。

### 步骤 6：验收与归档

全部产出物齐备后，小陈在任务详情页手动将任务从「进行中」标记为「待验收」（待验收由成员手动标记，Agent 不自动触发）。随后小陈核对需求文档、设计文档、实现说明与验证结论，确认符合预期，将任务标记为「已完成」；后续经团队确认不再需要跟进，将其「归档」。归档后任务历史完整保留，产出物与版本可供追溯复用。

验收与归档在任务详情页完成，产出物列表与版本历史统一在文档库中查看，界面效果见下方原型预览：

```prototype
id: task-detail
title: 任务详情与文档库
device: desktop
height: 720
```

文档库集中承载全部产出物与版本，支撑小陈核对验收与后续追溯复用。

### 场景要点小结

- **协作衔接**：各环节通过「群聊 @ 触发 + 产出物入库」衔接，角色之间按需互 @，任务文档库是共享的全局上下文。
- **上下文连续**：私聊与群聊 @ 共用同一 Agent 会话，Agent 始终记得任务上下文。
- **过程可见但不打扰**：Agent 内部处理过程不广播到群聊，群聊只显示最终回复；用户可点击 Agent 实时查看其会话。
- **成果留痕**：结论文本直接归档、文档与文件经平台归档为产出物，带版本历史，支撑验收与追溯。
- **启动可控**：任务创建后处于「待开始」，由成员确认 Agent 团队与主 Agent 后手动触发开始；Agent 处理中提供 Loading 状态，异常时给出错误反馈并可重试，处理状态始终可见。
