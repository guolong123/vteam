## 三、问题清单

### P1【严重】会话复用导致 Agent 回复内容错乱
- **现象**：群聊/私聊复用同一 opencode session 后，agent 回复聚合了历史任务全部内容（`[群聊历史消息]` + `<doclib>` 注入 + 历史用户消息全部拼入 text），新任务回复返回旧任务内容。
- **证据**：
  - m_0000000103：新任务（e2e-doc 写文件）回复却是旧任务（bash 测试）的回复文本；
  - m_0000000106：私聊问"请介绍你自己"，回复却聚合了 bash 测试 + e2e-doc 产出物声明 JSON；
  - 群聊界面 m_0000000100/m_0000000103 文本含 2 段重复的 `[群聊历史消息]` 全文。
- **影响**：用户无法获得正确的 Agent 回复；聊天界面冗余难读。
- **建议**：回复聚合应只取当前轮次新增的 assistant 文本（按 part 时间过滤），或按 session 消息增量截取；会话复用时注入的上下文（doclib/历史）不得拼入最终回复文本。

### P2【严重】Agent 创建的文档无法访问（核心问题）
- **现象**：
  - agent 创建的文件落在 worker 容器 `/tmp/opencode/`，浏览器不可达；
  - 手动提交 doc 产出物后，fileRef 仅为路径占位：`sha256=e3b0c44298fc1c14...`（空内容哈希），`/uploads/english-mini-program-requirements.md` 返回 **404**；
  - server 容器无 uploads 文件（代码注释明确"Phase 3 不真实拉取"）。
- **影响**：用户从聊天/产出物页面无法查看 Agent 产出文档；下载链接点击即 404。
- **建议**：归档链路需真实上传文件到控制面（worker 完成时上传产物文件 → server 落盘 uploads → 生成可访问 URL），或提供文件代理读取通道（经 server 转发 worker 文件）；在未实现前，前端应对无真实文件的内容降级为纯文本展示而非可点击链接。

### P3【严重】产出物声明自动归档链路未生效
- **现象**：用户消息明确要求回复时声明产出物 `{"type":"doc","title":"端到端文档测试","fileRef":"/tmp/opencode/e2e-doc.md"}`，agent 回复文本中确实出现了该 JSON（m_0000000106），但产出物列表仍为空。
- **根因**：归档依赖 worker 回流 `payload.artifacts` 数组 + server 端 `extractArtifacts(text)` 提取。实际链路未打通（worker 可能未提取，或回复文本聚合错乱导致声明未随正确回流到达）。
- **影响**：产出物只能靠成员手动旁路提交（POST /tasks/:id/artifacts），Agent 自动产出不可用。
- **建议**：worker 端增加产出物声明提取并随 task.completed 回流；修复 P1 文本聚合后再验证 extractArtifacts 链路。

### P4【严重】模型首字超时导致任务执行失败且无反馈
- **现象**：新任务 t_0000000004 执行中 worker 日志：`[prompt-await] 会话 ... 等待首字超时（可能模型无响应或会话挂起）` → `abort` 会话；消息 m_0000000109 **永远停留在 processing 状态**，界面无失败提示。
- **影响**：用户误以为 Agent 还在处理，实际已失败；失败执行不产生任何反馈与产出物。
- **建议**：首字超时/执行失败时向群聊写入失败状态消息（如"Agent 执行失败：超时"），并将 processing 消息终态化为 failed。

### P5【中】Worker 心跳不稳定
- **现象**：worker 心跳多次失败：`fetch failed` / `HTTP 408 Request Timeout` / `HTTP 500`；server 端 Prisma 连接池超时（`connection pool timeout, limit 33`）。
- **影响**：Worker 状态可能误判离线，任务调度可靠性下降。
- **建议**：排查 server 数据库连接池配置（连接数/超时）与 worker 心跳超时设置。

### P6【中】群聊回复文本拼接全局消息（用户提交需求 ①）
- **现象**：`[群聊历史消息]` + `<doclib>` 注入内容直接拼进 Agent 回复 text，在聊天界面渲染为正文，非常难看。
- **用户要求**：维护一个全局消息（separate system message），由系统自动注入到 Agent 上下文，**不拼进 AI 回复文本**。
- **建议**：将历史上下文/文档库内容改为独立注入（如 system message 或隐藏 part 类型），聚合文本时排除该类型。

### P7【低】产出物协议 + @机制需注入全局提示（用户提交需求 ②）
- **现象**：Agent 默认不按产出物协议回复（本次测试显式在用户消息中给出 JSON 声明后才出现），@ 定向机制 Agent 侧无明确说明。
- **用户要求**：将产出物协议格式（text/doc/file + fileRef 声明）与 @ 定向机制说明放入 Agent 的全局提示（system prompt），让 Agent 知晓该用何种格式产出可归档内容。
- **建议**：在 Agent prompt 模板（server 侧下发 worker 的全局提示）中追加产出物协议章节。

### P8【低】侧边栏导航被内容区拦截
- **现象**：从任务详情页点击侧边栏导航按钮，报 `intercepts pointer events`（app-content / navdock-icon 遮挡），点击失败。
- **影响**：需改用 URL 直接导航绕过；影响用户体验。
- **建议**：检查 nav-dock 与 app-content 的 z-index/布局，消除遮挡。

## 五、建议修复优先级

| 优先级 | 问题 | 理由 |
|--------|------|------|
| P0 | P2 文档无法访问 + P3 归档链路 | 用户核心诉求：Agent 产出物可访问、可归档 |
