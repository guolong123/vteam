1. BYTE CAP IS REAL  (C)
-------------------------------------------------------------------------
Code path: realtime.service.ts:293-316 (retainInLog / evictLogHead) with the
parallel bookkeeping fields at :151-156 and the measurement helper at :319-326.

* BOTH caps enforced, head-first. retainInLog pushes, then runs two sequential
  loops:
      while (this.log.length > this.maxLog)            this.evictLogHead();   // :298-300  (count cap, DEFAULT_MAX_LOG=1000 :52)
      while (this.logBytesTotal > REALTIME_LOG_MAX_BYTES
             && this.log.length > 1)                   this.evictLogHead();   // :301-306 (byte cap, 8 MiB :95)
  Eviction is exclusively `log.shift()` + `logSizes.shift()` at :311-316 — head
  only, so the surviving segment preserves relative order (id ascending, since
  ev_ ids are zero-padded and lexicographic == numeric).

* Newest entry always retained. Both loops run AFTER the push, and the byte
  loop carries the guard `this.log.length > 1` (:303). A single entry larger
  than the 8 MiB budget is therefore still kept; log length is never 0 after
  the first emit. Asserted by byte-cap.spec.ts:152-170.

* getLatestId() cursor survives. getLatestId (:518-523) reads
  `this.log[this.log.length - 1].id`. Because eviction is head-only and always
  leaves >=1 entry, the tail is always the newest emitted id. byte-cap.spec.ts:
  121-136 and :145-149 pin it.

* Parallel-array accounting cannot drift. logSizes.push happens in the SAME
  synchronous statement block as log.push (:294-297), and evictLogHead is the
  only remover, shifting BOTH arrays in lockstep (:311-315). There is no other
  mutation site for either array (grep-verified). logBytesTotal is a running
  sum: += the measured size on push, -= the shifted size on evict — it can
  never go negative because only previously-added sizes are subtracted, and it
  can never double-count because each entry is subtracted exactly once.
  Independent-recompute cross-check exists at byte-cap.spec.ts:112-116:
      logSizesOf(service).reduce((a,b)=>a+b,0) === totalBytes(log)
      (service as any).logBytesTotal            === totalBytes(log)

* Non-JSON-serialisable payloads: measureRetainedBytes (:319-326) wraps
  `Buffer.byteLength(JSON.stringify(value) ?? '', 'utf8')` in try/catch and
  returns the conservative 4096 B fallback (:323-325). JSON.stringify throws
  TypeError on circular refs and on BigInt — both land in the 4 KB branch.
  (JSON.stringify(undefined) returns undefined, not a throw; the `?? ''` keeps
  that at 0 B.) Overflow/NaN never occur: byteLength is a byte count, always a
  finite integer. So accounting can never throw into the event stream.
