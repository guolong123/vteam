1. 实现要点
--------------------------------------------------------------------------------
- 新增 `WorkerClient.runSecretCommand(worker, opts)`：POST 到 exec 端点
  `/secret-command`，headers `Content-Type: application/json` + `X-Worker-Token`
  （复用既有 `requestExec` → `requestToUrl` 路径，Basic Auth/错误归一继承）。
- **显式请求超时**：`requestTimeoutMs = resolveSecretCommandTimeout(opts.timeoutMs)
  + SECRET_COMMAND_REQUEST_TIMEOUT_SLACK_MS`（= 命令超时 + 5000）。
  - 归一对齐 worker `normalizeTimeout`：缺省 60000，上限 600000（DEFAULT_SECRET_COMMAND_TIMEOUT_MS /
    MAX_SECRET_COMMAND_TIMEOUT_MS）。
  - 300s 命令 → 305000ms；缺省命令 → 65000ms；**两条路径都 > 默认 DEFAULT_REQUEST_TIMEOUT_MS(60000)，
    绝不使用 4 参缺省的 60s**（第 4 个 requestExec 参数显式传入）。
- 失败归一：非 2xx / 网络失败 / 超时 abort / 200 非 JSON / 200 缺 status
  → 一律 `WorkerUnavailableException`（503），`httpStatus` 保留 worker 原码（400/409/500）。
- 不泄露：请求体含明文 secrets → 方法内**零日志**；非 2xx 分支不读响应体、
  异常 detail 只带状态码（`secret-command HTTP <status>`），不回显请求体/响应体。
- `describeError(err, timeoutMs?)` 增加可选参数（默认值不变），超时文案报出
  **真实生效超时**（`请求超时（>305000ms）`），不再误导为 60000ms；既有调用点与
  既有断言（`请求超时（>60000ms）`）不受影响。
- 类型：`SecretCommandRequest` / `SecretCommandResult` **双写**自
  `worker/src/protocol/worker-protocol.ts` 的 `SecretCommandRequestPayload` /
  `SecretCommandResponsePayload`（`SensitiveCommandInput`/`SensitiveCommandOutput` 派生）。

  ⚠️ 决策（为什么双写而不是跨包 import）：实测 server tsconfig 无 rootDir/include，
  一旦 `import type ... from '../../worker/src/protocol/worker-protocol'`，
  tsc common root 从 `server/` 抬升到仓库根，输出布局由
    /tmp/probe/src/main.js  →  /tmp/probe/server/src/main.js（且出现 worker/ 目录）
  （命令：`npx tsc -p tsconfig.build.json --outDir /tmp/tsc-probe-* --listEmittedFiles`）
  —— 会破坏 dist 布局与 nest/Docker 启动。仓库既有约定即双写 + 互通 spec
  （`server/src/workers/dto/worker-dto.spec.ts:10`、`worker/src/protocol/contract.spec.ts:341+`）。
  探针临时文件已删除，`npx tsc -p tsconfig.build.json --noEmit` exit 0。
