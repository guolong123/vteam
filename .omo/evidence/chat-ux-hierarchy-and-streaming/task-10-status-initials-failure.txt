1. 红跑构造（先写测试，实现严格在红之后）
======================================================================
步骤与顺序（两条红各对应各自的实现缺口）：
  1) 写 web/lib/message-initials.spec.ts（7 例）→ 立刻跑 → 红①：
     模块不存在（Cannot find module './message-initials'）。
  2) 写 web/e2e/chat-density.spec.ts 的 B7/B8 7 条测试 + 6 个 fixture kind
     （此时 ChatBubble 仍无 status/initials、MsgParts 仍无 initials）。
  3) 落 web/lib/message-initials.ts（纯函数，B8 的生成规则）——只为了让测试缝能打包，
     **组件一行未改**；随后跑 chat-density → 红②（断言级红，见 §2）。
  4) 最后才改 chat-bubble.tsx / msg-parts.tsx / session page.tsx → 绿。
为什么分两段红：chat-density 的 HARNESS_SOURCE 用 esbuild-wasm 静态 import 生产组件与
lib/message-initials；若连模块都没有，整份 harness 打包失败，红点会退化成「构建错误」而非
「行为断言」。先落纯函数、后改组件，可以让 B7/B8 的**行为断言**在改动前逐条见红，
同时 lib spec 自己的红（模块缺失）已经先行记录。两段红都不含任何产品组件改动。

诚实说明（测试文本的一处笔误修正）：
  lib spec 初稿把 messageInitials("aaron") 期望写成 "AR"（实为 a,a → "AA"），
  在模块落地后的首轮 lib 跑里由 1 failed 暴露，按既定规则「前两个字母大写」改为 "AA"；
  这是测试作者算术笔误，不涉及放宽任何 B7/B8 判据（distinctness 用 Alice/Aaron → AL/AA 仍然成立）。
  修正后 lib 7/7 绿，此后 lib 测试文本不再变动。
