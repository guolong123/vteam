8. IMPLEMENTATION SUMMARY (semantics as built)
=============================================================================
- `AssignmentRequirement.preferredWorkerId?: string` — within-candidates preference only.
- assignWorker: `ranked` chain keeps ALL FOUR filters unchanged
  (① status!==offline ② remainingCapacity>=need ③ opencodeVersion ④ matchesModelRequirement).
  Pin lookup happens INSIDE the post-filter `ranked` array, so a pin can never bypass a filter.
- Miss => logger.warn + return existing `ranked[0]?.worker.id ?? null`. Never throws.
- Warn reasons: if the row IS in the raw candidate list but was filtered out, the warn prints
  the concrete failing predicate values (status / capacity / opencodeVersion / modelId);
  if absent from candidates it says "不在候选集中（行缺失或已 offline，二者不可区分）" — matching
  the plan's constraint that the DB `where` already excludes offline, so the two are
  indistinguishable in the candidate set.
- degraded pin: passes all four filters (only offline is excluded) and bypasses online-first
  sorting -> still returned, but warned about.
- B1 (pin-only, does NOT touch matchesModelRequirement): if req.modelId is set and the pinned
  worker has modelAvailabilities.length === 0 (never reported) -> treat as a miss and fall back.
  Rationale (in code comment): matchesModelRequirement returns true for never-reported workers
  (avail.length===0 => true, a published transition-period contract); harmless under auto-
  scheduling, but a pin turns it into a deterministic selection and would silently defeat the
  published model-availability guarantee, deferring failure to opencode serve runtime.
  Also noted in the comment: a worker with defaultModelId === modelId and zero availabilities
  passes filter ④ but is rejected by B1 — intentional; the fallback re-rank may still pick it
  back, and that is not a bug.
- `remove()` (:1310-1325) NOT touched (owned by Todo 6, must land with the schema columns).
