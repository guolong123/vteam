## 二、根因（证据链）

**handleTaskCompleted 复用了跨轮次残留的旧 processing 消息 m_526**：
1. m_526 是 20:43 某轮 dispatch 的 delta 创建的 processing 消息（后续 agent 失败/中断，
   failProcessingMessage 只标记最新一条 processing，m_526 未清理而残留）；
2. 21:48 新一轮 dispatch → agent 回复 → handleTaskCompleted `findFirst({channelId,
   senderType:agent, senderId, status:processing})` **命中残留 m_526** → update 终态化，
   **createdAt 保留 20:43**（旧时间）；
3. SSE 广播 `chat.message.new` 的 `message.createdAt=20:43`；
4. 前端 `mergeSnapshotWithLive` 按 `createdAt` 排序（serve 快照 + 平台增量混合需时间序）→
   **新回复被排到历史中间（页面索引 20），页面底部不出现新消息**；
5. 用户视角：SSE 事件接口持续返回数据（loading/delta/chat.message.new 都有），但底部无刷新。

## 三、修复（最小，server 端）

`server/src/chat/worker-dispatcher.ts` dispatchForTarget 内，execute 之前：
```ts
const cleanupChannel = await this.resolveChannel(taskId, target.agentId, session.taskAgentId ?? undefined);
if (cleanupChannel) {
  await this.prisma.message.updateMany({
    where: {
      channelId: cleanupChannel.id,
      senderType: SENDER_TYPE.agent,
      senderId: target.agentId,
      status: MESSAGE_STATUS.processing,
    },
    data: { status: MESSAGE_STATUS.failed },
  });
}
```
原理：新一轮 dispatch 前清理目标频道残留 processing → 本轮回复要么新建（createdAt=本轮），
要么复用**本轮 delta 新建**的 processing → createdAt 正确 → 前端按时间正序排到底部 → 实时刷新。

配套：`worker-dispatcher.spec.ts` message mock 增加 `updateMany`（类型 + beforeEach 默认值）。

## 五、风险
- dispatch 热路径新增一次 `resolveChannel` 查询 + 一次 `updateMany`（channel 存在时）——
  频道路径已在前置步骤查询过，开销可忽略；清理命中为 0 时 updateMany 无副作用。
- failProcessingMessage 的「只标记最新一条」残留问题仍可能产生 processing 残留，
  但 dispatch 前清理已兜底，残留不会再被终端回复复用。
- 前端 `mergeSnapshotWithLive`/`upsertMessage` 无需改动（根因在后端 createdAt）。
