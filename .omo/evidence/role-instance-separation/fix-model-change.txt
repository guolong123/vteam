## 2. 修复方案与 diff

**无行为缺陷可修。** 补充模型日志（防御性改进，帮助用户/运维确认 serve 实际使用模型）：

### worker/src/driver/v1-driver.ts（sendMessage 日志加 model）
```ts
const modelLabel = input.model
  ? `${input.model.providerID}/${input.model.modelID}`
  : '(default)';
this.logger.info(
  `[v1-driver] sendMessage -> ${sessionID} model=${modelLabel} (HTTP ${res.status})`,
);
```

### worker/src/exec/exec-server.ts（执行日志加 model + describeModel 辅助）
```ts
function describeModel(model: DriverModelRef | null | undefined): string {
  if (!model) return '(default)';
  return `${model.providerID}/${model.modelID}`;
}
// 执行完成日志
`[exec] 执行完成 session=${opencodeSessionId} taskId=${payload.taskId ?? '-'} model=${describeModel(payload.model)} text=${result.text.length} chars`
```
`(default)` 标记是排障关键：当日志显示 `model=(default)` 即表示 dispatch 未传模型、serve 落入默认模型（gpt-5.6-luna）。

## 4. 用户问题可能原因分析（非代码缺陷）

1. **用户配置的模型与当前相同**（13:49 与 14:14 两次配置均为 flash，重发消息模型"不变"是预期的）
2. **配置的模型额度同样失效**：serve 日志显示 `opencode/deepseek-v4-flash-free` 报 `AI_APICallError: Rate limit exceeded`——若换的模型无额度/无凭据，serve 调用失败（表现为超时/错误），易被误判为"模型没变"
3. **available-models 返回目录全部 enabled 模型（不过滤 worker availability/凭据）**：用户可配置 worker 实际无法运行的模型（如 deepseek/deepseek-v4-pro 无凭据），配置后 dispatch 失败或 serve 调用失败

**排查建议**：用户配置模型后重发消息，通过 `docker logs aiagents-compose-worker | grep sendMessage` 直接确认实际使用的模型（本次新增的日志字段）。

## 5. Risks

- 日志改动仅影响输出格式（原 logger 无结构化消费方），不影响 sendMessage/execute 行为
- worker 容器已重建部署（镜像 aiagents-worker 重新 build）
- 环境模型已还原为全 flash，无残留改动
