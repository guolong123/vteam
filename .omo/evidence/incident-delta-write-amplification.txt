incident-delta-write-amplification.txt
TASK: cut per-delta write amplification in server/src/workers/worker-event.ingress.ts
ROOT CAUSE: on EVERY message.part.delta the ingress merged the increment into the
  in-memory assembled state AND wrote the FULL accumulated content back to the
  `messages` row. Measured today: messages.ibd 3.57 GB / 2848 rows (~1.25 MB/row);
  MySQL row-based binlog ~1 GB every 2-3 min (~20-30 GB/hour) because each UPDATE
  rewrites the whole row; that filled a shared 983 GB NFS volume to 100% →
  mysqld died `posix_fallocate ... error number 28` (ENOSPC) + signal 6,
  crash-looped, whole app returned HTTP 500.
  Emergency mitigation (NOT a fix) was already applied: 235 binlogs deleted
  (233 GB freed) + binlog_expire_logs_seconds=7200. ~231 GB free buys 8-11 h.
--------------------------------------------------------------------------------
CHOSEN DESIGN (3 parts)
--------------------------------------------------------------------------------
1. THROTTLE / COALESCE  —  `export const DELTA_PERSIST_INTERVAL_MS = 1000`
   The cache entry became a ledger (`AssemblingEntry`):
     parts      = in-memory TRUTH (post-merge, every delta)
     dirty      = true  <=> memory leads the DB row (skipped increments exist)
     lastFlushAt= Date.now() of last successful DB write
     row        = row returned by that last write (DB-side broadcast fields)
   Cache-HIT delta: merge into `parts`; if `Date.now() - lastFlushAt <
   DELTA_PERSIST_INTERVAL_MS` → SKIP the DB write, set dirty=true, and STILL
   broadcast, building the frame from `{...cached.row, content: <in-memory>}`.
   The MISS branch is deliberately NOT throttled (it re-establishes cache + needs
   a full DB row for the frame; it runs once per stream per process).
   WHY 1000 ms: 7-35 deltas/s → 7..35 increments coalesced into 1 write
   (write-count /7 worst case, /35 best); SSE unaffected (1 frame per delta,
   payload synthesised from the same state the next write will persist); REST
   history at most 1 s stale (only visible if the user reloads mid-stream);
   crash exposure bounded to the last <1 s of increments and the leftover row
   stays status=processing so the D2 sweep fails it instead of presenting a
   truncated message as complete.

2. GUARANTEED FINAL FLUSH on every terminal path
   - task.completed            → `await this.flushAndDropDeltaStream(key)`
   - agent.status{status:error}→ `await this.flushAndDropDeltaStream(key)`  (D1)
   - dispatcher watchdog/stale-row sweep
                               → `invalidateDeltaStream()` guarded flush     (D2)
   `flushAndDropDeltaStream` runs INSIDE the stream key's own exclusive chain
   (`runPartDeltaExclusive`), so an in-flight delta write lands first, the flush
   then sees the freshest assembled state, and the cache invalidation (delete)
   also happens inside the chain — a queued same-key delta necessarily MISSes
   after it. Both ordered paths flush BEFORE `notify(...)`/`realtime.emit`, i.e.
   before the dispatcher finalises the row, so they use plain `message.update`.
   `invalidateDeltaStream` is a SYNC hook whose caller (worker-dispatcher
   dispatchAgentMention stale-row sweep) marks the row `failed`/deletes it
   BEFORE calling it → its flush is `updateMany({where:{id, status:processing}})`
   (GUARDED): already-final rows are 0-row no-ops, so streaming content can
   never be written over a `failed` row (the D1/D2 corruption class the
   pre-existing regression tests pin).

3. STALENESS HAZARD (mid-stream MISS cannot silently lose a middle chunk)
   Design = FLUSH-BEFORE-EVICT + RECOVERABLE-BY-CONSTRUCTION:
   - `cacheAssembled` no longer drops the oldest entry silently. If it is dirty
     it is flushed first, and the flush is enqueued on the EVICTED KEY'S OWN
     chain: while that chain entry exists, any same-key delta queues BEHIND the
     flush (its MISS read therefore sees the fully-flushed row); if the chain
     has already self-cleaned, the flush had already landed. Either way the
     subsequent MISS cannot read a row that is missing the tail.
   - The eviction/D2 flush is guarded (status=processing): if the stream was
     already finalised, the write is a 0-row no-op (nothing to preserve).
   - On flush FAILURE the tail is dropped with an error log and the entry is NOT
     re-inserted (re-inserting would let a later delta HIT the cache and
     `message.update` a possibly-finalised row — reopening the D1/D2 hole).
     This degrades exactly to the codebase's documented "event replay is
     best-effort" posture instead of corrupting a final row.
   - RESIDUAL EXPOSURE (process restart): the cache is in-memory, so a crash can
     still lose at most the last <1 s of increments for streams that were
     mid-flight at that instant. This is unrecoverable in-memory by construction
     (any durable recovery would require writing every delta, i.e. the very
     amplification being removed). Bounded by the 1 s window; the leftover row
     stays `processing` and is failed by the existing D2 sweep rather than being
     presented as complete.
