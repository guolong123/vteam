## (e) Rollback exercise (on a COPY) — PASS

Two documented rollback paths, BOTH exercised on scratch databases only. The live DB was never
targeted.

### A. 0008 documented reverse SQL (role_prompt -> NULL), on `aiagents_t8` (the post-migration copy)
```
before: builtins non-empty role_prompt = 7
$ UPDATE agent_roles SET role_prompt = NULL WHERE `key` IN (...7 builtin keys...);
after:  builtins non-empty role_prompt = 0
builtin rows kept        = 7      (identity rows survive)
team_members still linked = 30    (role_id untouched by this path)
```
FINDING (recorded, not hidden): the 0008 migration header documents the reverse as
`... WHERE key IN (...)` WITHOUT backticks. `key` is a MySQL reserved word, so the literal
documented statement errors `ERROR 1064 (42000) ... near 'key IN'`. The backticked equivalent
(`WHERE \`key\` IN (...)`) runs clean (exit 0). The rollback PATH is sound; the header snippet
needs backticks. I did NOT edit the migration (out of scope for a proof todo) — recorded here.
