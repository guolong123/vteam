2. 新增 memory-maintenance.service.ts
====================================================================
`server/src/memories/memory-maintenance.service.ts`（+ 同名 spec，25 用例）

## onModuleInit 三件事
1. `registerHandler(TRIGGER_KIND.MEMORY_MAINTENANCE, handler)`
2. `registerGuard('memory_maintenance_cooldown', guard)` —— 冷却窗口拒绝重入：
   - `running` 为真（上一轮未跑完）→ 否决，留 pending 待下轮复核；
   - 距 `lastRunAt` 不足一个 interval → 否决（ticker 重入 / 手动与定时撞车）；
   - 异常 → fail-open 放行（对齐 progressionCooldownGuard 惯例）。
3. 全局单行排期（抄 `hook.service.ts:923-948 ensureGlobalPoll`）：
   - dedupKey 常量 `memory_maintenance:global:main`；
   - `schedule(kind, dueAt, payload, dedupKey, {intervalMs, guardKey})`；
   - 幂等：既有 pending 行原样保留（fireCount 不清零）；
   - 既有终态行先删后建（否则 dedupKey 幂等回旧行，改 env 后永不生效）；
   - `intervalMs <= 0` → 不排期 **且 cancel 既有非 cancelled 行**。

## env（校验惯例抄 trigger.service.ts:678-685 `scanIntervalMs`）
| env | 默认 | 语义 |
|-----|------|------|
| MEMORY_MAINTENANCE_INTERVAL_MS | 86400000（24h） | **0 = 禁用**（不排期 + 取消既有行） |
| MEMORY_ORG_UNUSED_DAYS | 30 | 低频未引用阈值（天） |
| MEMORY_ORG_CANDIDATE_LIMIT | 50 | 每团队候选清单上限 |

非法值（非数字/非有限）静默回落默认 —— 配置项不该让进程起不来（沿用既有惯例）。
非正数的 unusedDays / candidateLimit 亦回落默认（0 会让判定退化）。

接线：
- `docker-compose.yml` server env 段（`:75-81`，紧邻既有 SILENT_SESSION_WAKE_MS 块）；
- chart **存在 env 清单**（configmap `server.env.*` + values.yaml `server.env`）→ 已补
  `memoryMaintenanceIntervalMs` / `memoryOrgUnusedDays` / `memoryOrgCandidateLimit`。

## handler 单轮（a→e）
- (a) `memory.groupBy({by:['teamId'], where:{level:'team', deletedAt:null, teamId:{not:null}}})`
- (b) 每团队候选（**服务端只列清单，判断权全在 Agent**）：
  - `duplicates`：同 team scope 内同 `contentHash` ≥2 条；
  - `unused`：`refCount=0` 且 `lastUsedAt ?? createdAt` 早于 UNUSED_DAYS；
  - `untags`：`tags` 缺失/空/含 `howto|pitfall|constraint` 之外的值（Json → 内存过滤）；
  - 三组按「重复 → 未引用 → 标签」优先级去重（同一条只提示一次），整体 cap CANDIDATE_LIMIT；
  - 每条 `{id, excerpt(80字), tags, refCount, group, suggestedAction}`；确定性排序（`orderBy id asc`）。
- (c) 灰色 system 条（克隆 `task-progression.scheduler.ts:740-793 postStallNoticeToTeamGroup`）：
  `chatChannel.findFirst({teamId, type:'team_group', deletedAt:null})` → `message.create`
  （`senderType=system`、`senderId=null`、`status=sent`）→ `realtime.broadcast(CHAT_MESSAGE_NEW, …)`。
  文案：`【记忆整理】本轮检测：疑似重复 X · 低频未引用 Y · 标签不规范 Z，已派发整理`
  **+ 上轮实际结果**（首轮省略该从句）。
- (d) 派发：`dispatchAgentMention({teamId, channelId, targetInstanceId: team.mainAgentMemberId,
  kind:'wake', text: prompt, internal:true})`；
  channelId 解析克隆 `task-progression.scheduler.ts:846-857`：**主 Agent private 优先 → team_group 回退**；
  `mainAgentMemberId` 为 null → logger.warn 跳过该团队（不落条、不派发）。
- (e) `lastRunAt` 更新（finally 内，进程内存态、无新列/无迁移）；
  **单团队 try/catch 隔离**：失败只 `logger.error`（带 stack），不影响其他团队。

## 「上轮实际结果」= 服务端 DB 统计（不依赖 Agent 回传）
`memory.count({level:'team', teamId, updatedAt:{gte: lastRunAt}, mergedIntoId:{not:null}})`
+ `memory.count({…, deletedAt:{gte: lastRunAt}})` → `上轮实际结果：合并 A 条 · 归档 B 条`。
Agent 不回复/超时/崩溃，留痕数字依然为真（plan 硬约束：报告不依赖 Agent 回传）。

## prompt 模板（中文，风格抄 triggerMemoryHarvest :800-819）
说明本轮任务 + 平台只列候选/判断归 Agent → ① `vteam_memory_search` 逐条核对
→ ② 语义重复 `vteam_memory_merge` → ③ 低价值/过时 `vteam_memory_archive`
→ ④ 标签 `vteam_memory_update` 归一到 howto/pitfall/constraint
→ ⑤ **单轮上限 20 条**（超出显式告知「留待下轮，不要赶工」）
→ 收尾要求简要汇报 + 「不该动」的条目及原因 + 禁止动 global/role 级。
