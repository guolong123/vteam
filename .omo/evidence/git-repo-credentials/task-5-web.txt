§5 server API 冒烟（curl + admin token，13000）
---------------------------------------------------------------------
POST  /api/v1/git-repos  {repoUrl, authType:ssh_key, key, grantedAgents:[a_tester read/allow, a_developer write/ask]}
  → 201 {id:gc_..., repoUrl: 规范化去.git, authType, fingerprint:"----****----", grantedAgents:[{agentId,name,permission,effect}]}
  HAS_KEY_FIELD = False（响应无 key/credentialRef 明文）

GET   /api/v1/git-repos
  → 含该仓库行，grantedAgents 带 name（join Agent）

PATCH /api/v1/git-repos/:id  {grantedAgents:[a_tester write/ask, a_developer read/allow]}
  → 200，授权全量覆盖（先软撤旧 + 建新）
  二次 PATCH（全量覆盖仅 a_developer read/allow）→ 200（幂等重建）

DELETE /api/v1/git-repos/:id
  → {id, revokedAt}；GET 后该仓库消失

member GET /api/v1/git-repos → 200（成员只读）

§6 越界修复：server PATCH 授权重建 500（TODO 2 遗留缺陷）
---------------------------------------------------------------------
现象：PATCH /git-repos/:id 更新授权 → 500 "Unique constraint failed on uk_git_repo_grants_agent_repo"
根因：GitRepoGrant 唯一约束 @@unique([agentId, repoUrl]) 不含 revokedAt；授权全量覆盖流程
      「updateMany 软撤旧授权 → createGrants createMany 新授权」时，软撤行仍占唯一索引，
      同一 agent+repo 的新行 createMany 撞约束 → 500（POST 覆盖激活历史仓库同样命中）。
      spec 因 mock prisma 未暴露 DB 约束而未捕获。
修复：createGrants 在 createMany 前 deleteMany 该 repoUrl 下已软撤占位行（revokedAt != null）。
      update 授权重建与 create 覆盖激活两条路径统一受益；DELETE 软撤销语义不受影响。
验证：server tsc 0 错误 + 30 个 spec 全绿；重建 server 后 PATCH 两次覆盖重建均 200。
说明：此修复属同一需求（git-repo-credentials）范围，阻塞本任务 VERIFY 核心步骤
      （PATCH 更新授权冒烟），已最小化改动并同步 spec，特此披露。
