【端点】GET /api/v1/teams/:teamId/coordination-metrics
        鉴权：AdminGuard（平台管理员 users:manage / permissions.all）——
              复用仓库既有 admin 端点护栏（memories.controller.ts 同款），
              **未新造任何权限键/能力点**，未收窄任何权限。
        参数：windowHours（1..720，缺省 168=7 天；超限 400，不静默截断）、
              to（ISO-8601 窗口右端点，缺省=现在，用于复现历史窗口）
        只读：零写入、零状态、零定时任务、无新表、无 migration。

【为什么按窗口而不是全量】三张事实表（messages / artifact_versions / message_receipts）
        都随时间线性增长；窗口不设上限 ⇒ 单请求扫描量无界。上限 720h（30 天）的依据：
        运营者复核「最近」的合理视野是上个月；量级估算 ≈ 77 条 agent 消息/天 ⇒
        上限窗口 ≈ 5.5 万行扫描，且聚合全部在 DB 侧完成。

五、口径说明（读数前必读）
------------------------------------------------------------------------------
1. **消息归岗按 sender_id（执行 Agent），不按 sender_instance_id。**
   实测依据：3 条 tester 的回信落在 PM 的私聊频道（sender_id=a_tester，
   sender_instance_id=PM 成员）。按实例归岗 PM 会虚高到 109，按 Agent 归岗是 106
   —— 106 才是计划里记的基线口径。
2. **一个 Agent 被多个岗位复用**时归「岗位序最靠前」的那一个（sortOrder，再按 key 兜底），
   保证「岗位分解之和 == 全团队 agent 消息数」，不重复计数。
   实测：a_developer 同时被 developer/plan 两个岗位的成员使用 ⇒ 归 developer。
3. **产出物的作者记在版本行**（artifact_versions.author_agent_id；artifacts 本体无作者列）。
   本数据集 7 个产出物的作者全为 NULL ⇒ 全部落 unassigned 桶、PM 产出物 0。
   「PM 产出物 = 0」在这里**同时**因为「PM 没产出」与「产出物没记作者」，指标本身仍是对的
   （PM 确实一条都没提交），但要意识到该数据集无法区分这两种 0。
4. **派发口径**：`message_receipts` 中 kind=dispatch 且 from_instance_id = PM 成员的行数
   = 定向派发次数（一次 fan-out 多目标 = 多行 = 多次派发）；派发通告消息数按 messageId 去重。
   「亲做」= PM 消息数 − 派发通告数（派发通告本身是「派活」，不是亲做）。
5. **双报口径**：主指标是**粗口径**（私聊占比 + 群私条数比）；另附**精确同文**（归一化空白后
   逐字相同、且同时出现在群聊与私聊频道）作为**下界**。
   为什么精确口径测不出：线上 PM 的私聊多为「已在群聊回复：……」的**转述**，逐字不同 ⇒
   实测 exactTextOverlap=0，而私聊占比 36.8% 说明双报确实存在。
   ⇒ **解读时以粗口径为主，精确值只当下界**（它回答「有没有逐字照抄」，不回答「有没有双报」）。
   要拿到真正的「同一结论」需要语义比对或「群帖→私帖」引用关系，**那需要新表/新字段**，
   本批硬约束禁止 ⇒ 未做，报告在此。
6. **分母口径**：本端点按「团队频道 + 窗口」统计 ⇒ 分母 154；计划里的 155 是全库口径。
   差的 1 条（m_0000000280）是 e2e 残留消息，落在另一个团队 tm_0000000002 的群聊频道，
   不属本团队 ⇒ 团队视角下不应计入。分子 106 两者一致。

六、已知残留 / 请编排者复核
------------------------------------------------------------------------------
1. **缺 (channel_id, created_at) 复合索引**：messages 现只有 (channel_id, id)、
   (task_id, created_at)、(channel_id, task_id)。本端点按「团队频道 + 窗口」过滤时，
   MySQL 走 (channel_id, id) 定位频道后仍需逐行过滤 created_at ⇒ 单次扫描该频道全部历史。
   有界（窗口 ≤ 720h + 团队频道集合），但大团队上仍是频道全量扫描。
   彻底解法是加 migration 建 (channel_id, created_at) 索引 —— **本批禁止建 migration**，未做。
2. **UI 有意不做**（web/** 未碰）：本批是服务端观测面，前端指标面板留待后续。
3. **无历史快照**：本端点只回答「此刻的窗口内」，不做趋势存储（要趋势需新表，本批禁止）。
4. **PM 阈值未硬编码**：除「PM 产出物 = 0」这一计划给定的硬目标外，消息占比/双报率
   **不设阈值**（只给基线与 note）——阈值是运营决策，不该由实现替用户定；
   若要告警，建议由调用方按 note 里的基线自行判定。
5. **同文判定用了一条 raw SQL**（$queryRawUnsafe + 占位符，无字符串拼接）：MySQL 方言
   （JSON 提取 + REGEXP_REPLACE）⇒ 若将来换 PG/SQLite 需改写；失败时降级为 null + WARN，
   不影响其余指标。
6. **私聊频道语义**：本数据集里 PM 的 39 条私聊是 PM 自己在自己私聊频道发的
   （「已在群聊回复：…」类转述），不是「别人私聊 PM」⇒ 私聊占比读作「PM 的协调输出里有多少
   团队看不见」，而不是「PM 私下说了多少悄悄话」。若将来私聊语义变化，指标口径需同步复核。
7. **admin 门按 AdminGuard 口径**（permissions.all 或 users.manage）：与既有 admin 端点一致；
   未新增权限键，符合「不收窄权限、不发明能力点」的硬约束。
8. **团队模块归属**：本批把端点放进既有 TeamsModule（而非新开模块）——团队维度的读本就属于

   新开模块只会多一次 app.module 接线。若编排者希望独立成模块，迁移成本很低
   （service 不依赖 TeamsModule 的任何东西，只依赖全局 PrismaService）。
