## Q1 — Triplet（§3.2）： verdict = 基本 PASS，带 2 个 gap 备注

**PASS 部分**：派发侧三元组 `round + planVersion(+hash) + expected` 被强制要求并正确消费。

- 解析器要求四项齐全，缺一即 `ok:false` —— `server/src/chat/review-dispatch-triplet.ts:62-99`：
  > `export function parseReviewTriplet(...){ ... const roundMatch = ROUND_RE.exec(text); ... const versionMatch = VERSION_RE.exec(text); if (!versionMatch) { missing.push('planVersion'); } const hashMatch = HASH_RE.exec(text); if (!hashMatch) { missing.push('planHash'); } ... const members = expectedMatch?.[1]?.match(MEMBER_RE) ?? []; if (members.length === 0) { missing.push('expected'); } ... }`
- 唯一 choke 点落在 `notifyAgent` 的 `kind==='review'` 分支，缺三元组拒绝触发并回精确 hint —— `server/src/platform-mcp/platform-mcp.service.ts:1202-1217`：
  > `if (kind === 'review') { const triplet = parseReviewTriplet(args.content); if (!triplet.ok) { ... return { ... triggered: false, reason: 'review-triplet', hint: REVIEW_TRIPLET_HINT, ...}; }`
- 通过后消费三元组开轮：round / planVersion{version,hash} / expected / collecting / timeoutAt 全写账本并排超时 timer —— `platform-mcp.service.ts:1482-1507`：
  > `await this.rounds.applyRoundUpdate(hostIssueId, { round: triplet.round, planVersion: { version: triplet.planVersion, hash: triplet.planHash }, expected: [...triplet.expected], ... status: 'collecting', timeoutAt: timeoutAt.toISOString(), });` + `await this.scheduleReviewRoundTimeout({... round: triplet.round, timeoutAt })`
- hash 单列必填与 §3.2 `planVersion(+hash)` 一致，不算收紧；`expected` 要求至少一个 `tmm_` id（`triplet.ts:82-85`），与 §3.1 名单形态一致。
- 未接受 §3.2 禁止之物：无效派发触发被拒（`triggered:false`），消息落库不断言回滚（注释已声明，`platform-mcp.service.ts:1201`）。

**备注（不推翻 PASS，详见 §Q6 G4/S1）**：choke 点只覆盖 `notify_agent kind=review`，`group_post` 的 @ 触发走 `kind='wake'`（`platform-mcp.service.ts:801-808`）绕过三元组门与开轮；回执侧版本号解析要求 `@ v<x>` 形式（`review-verdict.listener.ts:34-35`），裸 `v0.3` 无 `@` 会被当缺版本打回，属可接受的严格化。

## Q2 — 回执校验门（§3.3）： verdict = PASS（三条全通）

**(a) 缺版本 → 打回、不计数** —— PASS。`gate.recordVerdict` 在任何写之前返回：`server/src/issues/review-round-gate.service.ts:162-175`：
> `const stated = (input.version ?? '').trim(); if (!stated) { const ledger = await this.readLedger(issueId); ... return { outcome: 'missing-version', ledger, converged: false, hint: \`打回：成员 ${input.member} 的回执缺版本号...\` }; }`
转发侧缺版本也如实转发（由门层打回，不丢弃）：`review-verdict.listener.ts:111-124`（`parsed.version ? {..., version} : {member, verdict, msgId}` + `await this.gate.recordVerdict(issueId, input, notify)`）。

**(b) 版本 ≠ 当前 → superseded 归档、不触发修订** —— PASS。账本层裁决：`server/src/issues/review-round-ledger.ts:392-404`：
> `const stated = (input.version ?? '').trim(); if (stated !== ledger.planVersion.version) { const superseded = [...(ledger.superseded ?? [])].filter(...); superseded.push({ member, verdict, msgId, version: stated }); return { outcome: 'superseded', ledger: { ...ledger, superseded } }; }`
门层 `outcomeOf` 据此判定（`review-round-gate.service.ts:327-336`），且 superseded 路径不碰 `received`、不走收敛分支（`recordVerdict` 仅在 `isConverged` 时翻转，`gate:180-183`）。精确覆盖 §4-2（m_510/m_498 分轮）。

**(c) 同轮同人多次 → last wins** —— PASS。`received` 按成员键覆盖：`review-round-ledger.ts:405-417`（`received: { ...ledger.received, [input.member]: { verdict, msgId, version: stated } }`），合并层同理（`mergeLedger`，`ledger:319-325`）。同 `msgId` 重复投递天然幂等。

附带说明：非 `expected` 名单成员的回执也会被记入 `received`（`resolveVerdict` 无成员资格检查），但 `isConverged` 只看 `expected ⊆ received`（`gate:282-287`），多余条目无害 —— 可接受简化。`pending-hash` 分支（`ledger:376-391`）在生产派发路径上实际不可达（开轮恒带 hash），属防御性死路径 —— 可接受。

## Q3 — 收敛门（§3.4）： verdict = FAIL（1 个 violation + 1 个 gap）

**收敛值正确一半**：`received ⊇ expected` → `complete`（非 `approved`），随后只到 `pending_final` —— `review-round-gate.service.ts:180-189` + `371-388`：
> `if (!converged || ledger.status === 'complete') { return ...; } const completed = await this.rounds.applyRoundUpdate(issueId, { status: 'complete' }); await this.markPendingFinal(completed, notify); await this.notifyConvergence(completed, issueId, notify, null);`
> `private async markPendingFinal(...) { ... await this.planSink.transition(taskId, PLAN_LIFECYCLE_STATUS.pending_final); ... }`
通知走两次 `kind='wake'`（计划员 + 抄 PM，`gate:390-415`），复用豁免路径，不记 throttle 预算 —— 与注释口径一致。

**Violation V1（否决级）**：收敛判定只看“人齐”，不看 verdict 极性 —— `gate:282-287`：
> `isConverged(ledger) { return (ledger.expected.length > 0 && ledger.expected.every((m) => ledger.received[m] !== undefined)); }`
全员 REJECT 的轮次同样 `complete` + 翻 `pending_final` + 通知“可修订”。但 §6.1 明确写的是“**轮次全部 APPROVE → 状态置 `pending_final`**”，且状态机中“评审 REJECT → draft”是回流分支。全 REJECT 轮次被置为待定稿、UI 冒出 [确认定稿] 按钮（`TeamRightPanel.tsx:558` 以状态为唯一条件），用户可把被评审否决的计划直接定稿 —— 与 §6.1 直接矛盾。

**超时路径代码本身干净**：`checkTimeout` 置 `stale` + 产出 wait/nudge/degraded-release 三选项（`requiresConfirm:true`），全程无 `notifier`/`planSink` 调用 —— `gate:217-239`；handler 非 `collecting` 一律 no-op 并委托判定 —— `review-round-timeout.handler.ts:89-99`：
> `if (ledger.status !== 'collecting') { return; } ... await this.gate.checkTimeout(issueId, new Date());`
“永不自动放行、永不通知计划员”属实。

**Gap G2（与超时相关）**：`stale` 的待拍板项无人能看见 —— handler 丢弃 `checkTimeout` 返回值（`handler:99` 无后续处理），`confirmDegradedRelease`（`gate:246-279`）零生产调用点（grep 仅命中 spec），无 API/页面入口。§3.4“转人工裁决”与 §4-4 在生产中无送达路径，超时轮次静默变 `stale` 后只能干等。

## VERDICT: REJECT

接线让死代码复活了（开轮、收 verdict、超时转 stale、收敛通知 + 翻 `pending_final` 全链路打通），C3 八项零收紧值得肯定，但两处硬伤不能放行：**V1**（`review-round-gate.service.ts:180-189,282-287`）——收敛判定不看 verdict 极性，全员 REJECT 的轮次同样置 `pending_final` 并通知“可修订”，用户可在 [确认定稿]（`TeamRightPanel.tsx:660-670`）把被否决的计划定稿，直接违反 §6.1“轮次全部 APPROVE → pending_final”；**V2**（`review-round-ledger.ts:316-318,353-358`）——升轮清零 `received/pending/superseded`，旧轮次“谁何时评了哪版”被覆盖销毁，直接违反 §3.4 归档句与 §4-3。另有四个 gap（G1 修订拦截零调用方导致 §4-1 未兑现；G2 超时拍板项无送达且降级放行不可达；G3 同轮重派发可撤销收敛；G4 `group_post` 派评审全程在账外）须在合入前或合入后首个跟进项中解决。修复 V1（收敛时要求全 APPROVE，否则保持 collecting/转 draft）与 V2（升轮前归档旧轮次明细）后可重审。
