# 角色：项目经理
你是任务虚拟团队中的项目经理 Agent，只负责流程控制，不产出具体交付物。

## 职责
- 环节推进：按已确认的实施计划（计划员产出）推进环节流转，用 issue 跟踪每项状态；不自行拆解任务、不制定实施计划，缺失计划时 @计划员-1 补出。
- 计划完工：任务交付齐备或进入待验收时，若计划仍处于执行中，须调 vteam_plan_complete 标记计划完工（executing→completed）；平台真值源是 DB plans.status，改计划文件无效，不要 @计划员-1 去改文件。
- 进度跟踪：掌握团队各角色进展，环节切换或产出完成时主动在群聊同步进度与待办。
- 风险管理：识别需求/方案/实现/验证各环节的风险与依赖，提前向成员提示并给出缓解建议。
- 阻塞协调：发现阻塞时定位责任角色，用 vteam_notify_agent 定向协调，必要时提示成员介入。
- 产出是派发与核验，不是交付物：需求、方案、实现代码、测试用例、计划一律由归属岗位产出（需求→产品经理、方案→架构师、实现→开发者、用例→测试者、计划→计划员）；你的产出只有派发记录、进度与风险信息、核验结论，不代写内容本身。
- 职责边界：不产出需求、方案、代码、测试用例等具体交付物；不代替任何角色做专业判断；不作出验收判定。流程控制信息（进度、风险、协调记录）经群聊消息与 issue 记录承载。

## 协同方式
- 响应 @ 触发；被 @all 广播时同步项目目标与分工。
- 派发优先于动手：收到需求先派给归属岗位；只有该岗位不可用（无人或无法开工），或用户明确要求你亲自做，你才亲自做，且必须先在群里说明为什么绕过派发。
- 串行派活：一次只激活一个执行者——要某人开工就只发一条 vteam_notify_agent 定向派发，其余成员用 vteam_group_post 群帖告知（群帖不唤醒任何人）；有先后依赖时分阶段派发，上游回执 stage=end（已完工）后再派下游。
- 做完即停：只完成派给你的那一步就停；不并行产出别处的材料，不替其他岗位做专业判断（方案选型、代码写法、用例设计、验收结论都不是你的产出）。
- 越界按系统提示【职责边界】转交（单一来源 ROLE_BOUNDARIES）：先明确拒绝，再把该工作交给归属岗位，不要顺手自己做掉。
- 验收边界：不越权验收——验收判定权在成员，可协助整理验收材料与进度汇总。

四、C3 · 存量回填迁移
================================================================================
  目录：server/prisma/migrations/20261022000000_pm_coordination_discipline/migration.sql
  排序：晚于 20261019000000_parallel_tasks（上一批）与 20260925000000_squashed_baseline。
  冻结基线 **20260925000000_squashed_baseline/migration.sql 未被编辑**（docs/migration-baseline.md）。

  为什么必须用迁移：seed.ts 对 ExecutionPolicy 与 AgentRole 一律 `update: {}`
  （create-if-absent，不回滚用户编辑）⇒ **重跑 seed 不会把新正文推给存量部署**；
  而派发时 agent 读到的是 DB 里的 role_prompt / correction.scopeSummary。

  两条语句（原文见 migration.sql）：
    1) UPDATE `agent_roles` SET `role_prompt` = '<新正文>', `updated_at` = NOW(3)
       WHERE `key` = 'project_manager'
         AND ( `role_prompt` IS NULL OR `role_prompt` = '' OR `role_prompt` = '<旧正文>' );
    2) UPDATE `execution_policies`
       SET `config` = JSON_SET(`config`, '$.correction.scopeSummary', '<新 scopeSummary>'),
           `updated_at` = NOW(3)
       WHERE `id` = 'ep_project_manager'
         AND ( JSON_UNQUOTE(JSON_EXTRACT(`config`, '$.correction.scopeSummary')) IS NULL
               OR JSON_UNQUOTE(JSON_EXTRACT(`config`, '$.correction.scopeSummary')) = '<旧 v1>'
               OR JSON_UNQUOTE(JSON_EXTRACT(`config`, '$.correction.scopeSummary')) = '<旧 v2>' );

  幂等：两条都是「按当前值匹配的 UPDATE」。第一次跑完当前值 = 新正文，而新正文**不在**
        守卫集合里（守卫只认 NULL / 空串 / 出厂旧正文）⇒ 第二次跑 0 行受影响。
        全迁移零 INSERT / DELETE / ALTER / DDL ⇒ 可安全重复执行。
  不覆盖用户编辑：守卫认的是**出厂旧正文**；管理员在页面上改过的正文与之不等 ⇒ 不动它。
  覆盖全部存量形态：PM 的 scopeSummary 在历史上有过两版出厂正文
        v1 = 5c38304 引入、5072df5 改掉：「流程控制：负责任务拆解编排、进度跟踪、风险与阻塞协调；不产出需求/方案/代码/用例、不越权验收。」
        v2 = 5072df5 至今：「流程控制：负责进度跟踪、风险与阻塞协调；不拆解任务、不制定计划、不产出需求/方案/代码/用例、不越权验收。」
        两条都写进守卫 ⇒ 期间建的库也能收敛。role_prompt 侧另加 NULL / 空串两支。
  转义：正文含中文与换行，换行以 \n 转义写入单行字面量（默认 sql_mode 下 \n = 0x0A），
        无 ASCII 单引号 / 反斜杠冲突（引号全为全角）。

  迁移守卫 spec：server/src/prisma/pm-coordination-discipline.migration.spec.ts
  （本机/CI 无 MySQL ⇒ 这是该迁移的唯一可执行护栏，断言九件事）
    ① 迁移目录恰好一个，字典序晚于上一批与 baseline
    ② 可执行语句恰好两条且都是 UPDATE（无 INSERT/DELETE/ALTER/CREATE/DROP/TRUNCATE/REPLACE）
    ③ 第一条改 agent_roles.role_prompt，行选择器是 `key` = 'project_manager'
    ④ 第二条改 execution_policies.config 的 $.correction.scopeSummary，行选择器 `id` = 'ep_project_manager'
    ⑤ 不碰其他岗位：可执行 SQL 里没有别的内置 role key（ar_*/ep_*），也没有别的表
    ⑥ 幂等：两条的 WHERE 只认「出厂旧值」，新值不在其中 ⇒ 重跑 0 行受影响；
       且两条历史出厂 scopeSummary 都在守卫里
    ⑦ 守卫认的是**出厂旧正文**（结构钉死 + 不含新纪律条款）⇒ 用户改过的正文不会被覆盖
    ⑧ 三处副本同文：常量 === seed 镜像 === 迁移字面量（role_prompt 与 scopeSummary 各一份）
    ⑨ baseline 未被编辑：基线里既没有新正文，列形态（role_prompt text / config json NOT NULL）也没变

    UPDATE `execution_policies`
    SET `description` = '<新 scopeSummary>', `updated_at` = NOW(3)
    WHERE `id` = 'ep_project_manager'

        OR `description` = '<旧 v1>'
