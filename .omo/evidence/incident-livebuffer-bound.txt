################################################################################
events() opens `const liveBuffer: RealtimeEvent[] = []` and pushes live frames while
`replaying === true`. The replay is `await this.realtime.getEventsSince(...)` inside
an async IIFE whose try/finally (landed in HEAD 00e4c68) resets replaying=false on

pool exhaustion, DB stall), neither the assignment nor the finally ever runs →
replaying stays true forever → the subscribe callback pushes EVERY live frame into
liveBuffer with no bound and no log. Each delta frame carries the whole accumulated
message (~250KB-1MB) at 25-44 frames/s → ~11-44 MB/s unbounded growth, silent.

# 3. NORMAL-PATH ARITHMETIC - a normal replay can never reach the caps
################################################################################
Frames enter liveBuffer ONLY while replaying===true, i.e. during the replay window:
    buffered_frames = frame_rate x replay_duration
    buffered_bytes  = buffered_frames x frame_size

Normal replay: getEventsSince reads <= REALTIME_REPLAY_MAX = 1000 rows (already
capped) with an indexed query and returns in milliseconds.

Worst NORMAL window (already 100x a typical ms-scale query): 100 ms
    frames = 44/s x 0.1 s = 4.4 frames
    bytes  = 4.4 x 1 MiB (1,048,576 B) = 4,613,734 B (~4.4 MiB)

Headroom vs the caps:
    count cap  REALTIME_LIVE_BUFFER_MAX_FRAMES = 1000
        1000 / 4.4 = 227x   (1s slow-but-fine replay: 44 frames -> 22.7x)
    byte budget REALTIME_LIVE_BUFFER_MAX_BYTES = 64 MiB = 67,108,864 B
        67,108,864 / 4,613,734 = 14.5x
        1s slow-but-fine replay: 44 x 1 MiB = 46,137,344 B = 44 MiB < 64 MiB
        -> still no eviction. Byte budget 64 MiB retains ~31-32 frames of 2 MiB
           (32 x 2,098,302 B = 67,114,464 B > 67,108,864 B -> head evicted to 31).

Worst retained after any overflow = budget + newest frame
    <= 67,108,864 + 1,048,576 + ~150 B header = ~65.1 MiB
    (length>1 guard keeps the newest frame; an oversized frame is kept exactly once)

Hung-replay (the Path F being closed): growth pinned at ~65 MiB vs pre-fix
    44 MiB/s x 60 s = 2,559 MiB/min  -> ~2.5 GiB/min (a 2 GiB cgroup OOMs in <1 min)
    65 MiB vs 2,559 MiB/min = ~39,000x tighter after 1 minute.

Replay deadline REALTIME_REPLAY_DEADLINE_MS = 30,000 ms
    30,000 ms = 300x the 100 ms worst-normal replay
              = 15x  a 2 s "slow but fine" replay
              <= 2 heartbeat intervals (HEARTBEAT_INTERVAL_MS = 15,000 ms)
    A legitimate slow-but-fine replay cannot reach the deadline; even if some
    pathological >30 s replay did, the semantics are safe (see section 5).

# 5. REPLAY DEADLINE SEMANTICS - exactly what happens if it fires early
################################################################################
The deadline can only fire when getEventsSince has not settled within 30 s, i.e.
the replay is hung (a legitimately slow-but-fine replay is <= s-scale; see #3).
When it fires, in order:
  1) replaying = false  -> every subsequent live frame passes straight through
     subscriber.next(toMessageEvent(event)); nothing is buffered any more.
  2) bufferReleasedByDeadline = true -> remembered for the settle path.
  3) warn (level "warn") -> the release is VISIBLE, not silent.
  4) the already-buffered frames are flushed immediately, in buffer order, which
     is arrival order == event emission order (eviction only removes from the
     head, so id order inside the buffer is preserved) -> no reordering.
  5) the buffer is emptied.
When the hung replay eventually settles, the settle path sees
bufferReleasedByDeadline === true and RETURNS BEFORE sending any backlog frame.
Why that is safe (exactly-once):
  * Events are persisted-then-broadcast in RealtimeService.emitOnce (create await
    completes, then bus.emit in the same microtask continuation).
  * Every backlog frame was therefore broadcast either before the deadline fired
    (-> it was pushed into liveBuffer -> flushed in step 4) or after
    (-> replaying was already false -> it went straight through).
    Even under DB-driver response reordering, a frame whose broadcast microtask
    has not yet run simply passes through live right after the settle.
  * Hence the late backlog is a strict subset of already-delivered frames;
    re-sending it could only duplicate (breaking the id de-dup semantics), so it
    is skipped entirely.
De-dup on the NORMAL path is untouched: whenever the replay settles before the
deadline (the normal case: milliseconds), bufferReleasedByDeadline is false and
the original backlog-then-dedup-buffer logic runs verbatim.
Residual edge (documented, degraded path only): if a team/task row is mutated so
that the bus-side scope filter and the DB-side backlog filter would disagree
DURING a >30 s hang, one frame could be missed on that connection only; the
normal path is unaffected and the client reconciles on reconnect.
