  the T10 dispatcher callback finalizes the message (status processing->sent).
  This is the load-bearing guard: without it a late post-completion delta would

  (FIFO via Map insertion order; skips the just-set key). Size is hard-bounded

  MISS next time — no data loss.

HARDEST QUESTION (a) stale/incorrect to a client:
  - After RESTART: cache is in-memory -> empty -> first delta MISS -> DB-authoritative. Safe.
  - After EVICTION: evicted key -> next delta MISS -> re-locate via findFirst. Safe.
  - Two streams interleaving on SAME channel+agent: they share ONE key/message, but
    this is IDENTICAL to the pre-cache DB locate (findFirst by channel+senderType+

5) BENCHMARK JUDGEMENT (with the realtime lane factored in)
--------------------------------------------------------------------------------
Executor micro-bench: 512 KB stream OLD ~1793 KB/delta -> NEW ~1281 KB/delta (-29%).
Is -29% meaningful at 80-110 MB/s? It is REAL and DIRECTIONAL: it deletes the single
findFirst full-content DB round-trip + Json deserialization per delta. But it is the
SMALLEST of the OOM amplifiers. The OOM was driven by ACCUMULATION, which the realtime
log comments name explicitly (realtime.service.ts:102-105): (i) realtime_events
persisted one full snapshot PER delta (26GB / 460k rows) and (ii) an in-memory log of
~1000 full-snapshot delta frames (~1GB). BOTH are fixed by the SIBLING realtime lane
(REALTIME_NON_RETAINED_TYPES: delta frames not persisted; compactDeltaPayload: log
keeps only messageId/channelId; REALTIME_LOG_MAX_BYTES byte cap).

Remaining per-delta cost AFTER BOTH fixes (all TRANSIENT, none accumulating):
  - mergePartsById(cached.parts,kept) :636  O(messageSize) in-memory
  - concatText(merged)               :641  O(messageSize) in-memory
  - message.update serialize full content :637  O(messageSize) write
  - toMessageDto clone :727 + live SSE fanout of full {message,delta} per subscriber
Nothing is RETAINED per delta anymore (no DB row, no full snapshot in the
bounded/compacted log). So the heap-growth / OOM driver is removed; what remains is
CPU/GC/DB-write pressure, which is survivable at 80-110 MB/s. => -29% is a genuine
improvement but is NOT the OOM fix on its own; the sibling realtime lane is. Together
the accumulation drivers are gone, so the incident is addressed.
Repro note: I did NOT run a faithful micro-bench — the eliminated findFirst READ and
the per-subscriber fanout cannot be measured cheaply/faithfully in this fully-mocked
spec harness; the -29% is verified code-wise + by the mutation-kill test instead.

NOTES (non-blocking, not part of acceptance)
--------------------------------------------------------------------------------
N1. Key-derivation divergence: handleMessagePartDelta applies the private-target
    override whenever team+member context exists (:591-601), while
    resolveDeltaStreamKey applies it ONLY for team_group sources (:792). If a delta's
    source were a private channel that is NOT the member's unique team-private
    channel, populate-key != invalidate-key and invalidation would miss (stale entry).
    Cannot occur under the model invariant (one private channel per team+member),
    so NOT a blocker — but aligning the two derivations would be cheap defensive
    hardening for the invalidation path.
N2. In-memory merge/concat remain O(messageSize) per delta on HIT. For a very long
    single stream this is per-delta CPU (transient, not accumulating). Acceptable now;
    revisit only if profiling shows it hot.
