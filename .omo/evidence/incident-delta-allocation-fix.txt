RULED OUT (checked, not the allocator):
  - Per-delta query returning many rows: none in the delta path (all findUnique/findFirst
    returning <=1 row). getEventsSince findMany is reconnect-replay only.
  - Unbounded in-memory buffer/array in ingress: the dedup window (isDuplicate :972) is
    bounded (DEDUP_WINDOW=1000) and partDeltaChains self-clean (:713). mergePartsById
    dedupes by id so content.parts does NOT accumulate duplicate snapshots.
  - WeCom relay / accumulating WeCom stream buffers: the delta-triggered callback
    worker-dispatcher.ts:4595 handleSessionActivity only re-arms watchdogs + persists a
    tiny session column. WeCom bridge (worker-dispatcher.ts:270/2098) is fed by FINALIZE
    (task.completed), not per delta. NOT in the delta path.
  - Per-subscriber copy of the payload: bus passes by reference; the cost is the
    per-subscriber JSON.stringify in toMessageEvent (SSE), still O(messageSize) each.

WHY it OOMs: RSS grew LINEARLY and was "largely OUTSIDE the V8 heap". Dominant retained
(external) drivers: (a) realtimeEvent.create persisting one FULL snapshot per delta, and
(b) the 1000-entry in-memory log ring buffer pinning ~1000 full snapshots. Under sustained
~35 events/s these prevent GC from reclaiming the transient, so the multiple per-delta
full-message encodes (read + merge + concat + 2 DB serializes + SSE) pile up until the
2 GiB cgroup limit. ~4 MB/delta == ~6x a ~0.6-1 MB streaming answer (see bench: a 512 KB
stream already costs 1793 KB/delta on the OLD path).

2. IS THE DELTA STREAM LEGITIMATE?  (NOT a runaway loop)
--------------------------------------------------------------------------------
Evidence (worker producer): server/src/driver/serve-event-stream.ts
  :223   if (!partID || !delta) return;         // empty deltas dropped -> strictly non-empty text
  :234   buf.text += delta;                     // monotonic accumulation
  :237-243 re-emits { id: partID, type, text: buf.text }  // SAME part id, GROWING text
So each delta carries the full-so-far text of a FIXED part id (text grows monotonically).
=> This is ONE long model answer streaming normally. The "same part id repeats" is BY
DESIGN (last-write-wins), not an error/retry loop. mergePartsById (message-parts.ts:88)
keeps one snapshot per id, so the message does not leak duplicates. The problem is purely
ALGORITHMIC: re-reading + re-serializing the whole-so-far message on every delta (O(N^2)
work for one answer), amplified 6x and by unbounded realtime retention.

3. FIX  (server/src/workers/worker-event.ingress.ts — surgical, in-memory assembled state)
--------------------------------------------------------------------------------
Add an in-memory assembled-state cache keyed `${targetChannelId}|${agentId}` (identically
to the existing serialization key), so the steady-state delta path does NOT re-read the
message from the DB and does NOT re-derive the whole message from a fresh DB read:

  * streamKey = `${channelId}|${agentId ?? ''}` (:624) hoisted (also the runPartDeltaExclusive key).
  * HIT fast-path (:628-650): if assemblingMessages has the key, merge the small `kept`
    delta into the cached parts -> message.update -> refresh cache. NO message.findFirst,
    NO merge-from-DB-read. Gates (hasRenderableContent) preserved.
  * MISS (:652-719): unchanged original findFirst -> merge/create, PLUS populate cache
    (cacheAssembled at :694 update + :715 create). MISS = first delta / restart / after
    task.completed, so a cold/restarted stream still resolves from the DB (correct).
  * cacheAssembled (:765-777): bounded (ASSEMBLING_CACHE_MAX=256); eviction of the oldest
    is SAFE — a later delta simply MISSes and re-reads from the DB.
  * invalidation (:787-795 + resolveDeltaStreamKey :741-815): on task.completed, compute
    the SAME target key (resolveChannel-equivalent) and delete ONLY that entry, so the next
    turn's first delta re-resolves from the DB (prevents updating a finalized 'sent' row).

The SSE/broadcast payload `{ message: toMessageDto(row), delta: kept }` is UNCHANGED ->
the visible streaming result is IDENTICAL (frontend use-realtime.ts:378-380 upsertMessage
still receives the full accumulated message each delta). Visible behaviour + DB persistence
cadence unchanged; only the redundant per-delta DB re-read + whole-message re-derivation are
eliminated ("reuse a cached assembled state").

Per-delta DB READS for the messages table drop to 0 on steady state (only the necessary
message.update WRITE remains). Routing reads (session/channel scoped to the stream) are left
as-is (small, and caching them risks the security + routing test invariants for ~no MB gain).

5. REPORTED NEEDED CHANGE (NOT made by me — server/src/realtime/realtime.service.ts is a
   PARALLEL-LANE-OWNED file; binding rule b)
--------------------------------------------------------------------------------
The SSE/UI contract REQUIRES the full {message:{content:{text,parts}}, delta} snapshot per
delta (frontend web/hooks/use-realtime.ts:378-380 upsertMessage replaces its cache with
payload.message). So the payload SIZE is fixed by the contract and CANNOT be shrunk in
ingress without breaking live streaming. The remaining dominant allocators are entirely in
realtime.service.ts (the replay-cap + retention lane):

  NEEDED CHANGE (realtime.service.ts):
   (1) emitOnce (:128-136) must NOT persist the full per-delta message snapshot to
       realtime_events. For type === MESSAGE_PART_DELTA persist a COMPACT/coalesced row
       (id/scope + delta, stripping message.content), and synthesize the current snapshot on
       reconnect replay (getEventsSince :235) by coalescing deltas up to the last snapshot /
       chat.message.new. This stops realtime_events growing one full snapshot per delta.
   (2) The in-memory `log` ring buffer (:62,:138-141) must NOT pin full-content delta
       payloads: either skip buffering delta events (rely on DB replay) or cap by TOTAL
       BYTES, not a fixed count of 1000 — otherwise it retains ~1000 full snapshots
       (~hundreds of MB, GC-pinned) which is the LINEAR RSS growth driver.
   (3) Add realtime_events retention (the lane's stated task).
  The `bus.emit` (:142) full broadcast to SSE subscribers stays unchanged (UI needs it);
  per-subscriber serialization (realtime.controller.ts:98) is inherent to SSE delivery.

With my ingress cache (removes the per-delta message re-read/re-derive = 29% less traffic)
PLUS the realtime.service retention/compact-persist lane (removes the retained full-snapshot
growth), the per-delta path stops amplifying memory and the OOM is eliminated while the
live streaming UI is byte-for-byte identical.
