--------------------------------------------------------------------------------
SERVICE IMPLEMENTATION NOTES
--------------------------------------------------------------------------------
1. Single query (comment in code explains the choice):
     prisma.modelUsage.groupBy({
       by: ['teamMemberId', 'model'],
       where: { teamId, ...(model ? { model } : {}) },
       _sum: { totalTokens, inputTokens, outputTokens,
               cacheReadTokens, cacheWriteTokens, cost }   // all `true`
     })
   `where:{teamId}` (+ optional `model` equality) matches the leading columns of
   idx_usage_team_member(team_id, team_member_id) and
   idx_usage_team_model(team_id, model). Aggregation happens DB-side, so only
   "member x model" aggregate rows cross the wire — never the team's raw usage
   rows (row count = call count, orders of magnitude larger).

2. Three-layer totals share ONE accumulator (addInto / normalizeBucket), so
   member subtotal = sum of its model buckets and teamTotal = sum of all rows
   are same-source by construction (asserted by a test, not just by prose).

3. Display names joined LIVE — never snapshotted:
     prisma.teamMember.findMany({ where: { id: { in: memberIds } },
       select: { id, agent: { name }, role: { name } } })
   model_usage has no FK, so a deleted member can still have usage rows:
   fallback agentName='' / roleName=null, numbers preserved.

4. cost convention (documented in code):
   model_usage.cost is NULL-able (NULL = upstream reported nothing = "unknown",
   not 0 = "free"). Prisma `_sum` returns null when every row in a group is
   NULL; normalizeBucket maps null -> 0 so NULL-cost rows PARTICIPATE AS 0 in
   every sum and the response cost is ALWAYS a number (web never needs a null
   branch). The unknown/free distinction survives at the detail-row level.
   No rounding is applied (raw accumulation; $ + 4dp display is web's job).

5. ?model= filter: trimmed; empty/blank = no filter (never yields empty results).

6. Deterministic ordering: members by totalTokens DESC, tie -> teamMemberId ASC;
   model buckets by totalTokens DESC, tie -> model name ASC. (Web need not re-sort.)

7. Empty team / no rows -> {members: [], teamTotal: all-zeros with cost: 0} and
   the member-name query is SKIPPED entirely.

8. Not aggregated: reasoningTokens. It is absent from the plan's response
   contract (the "6 fields" = 5 token counters + cost) and is already contained
   in totalTokens upstream, so exposing/summing it separately would invite double
   counting. Documented in the code comment. (Parent brief said "6 token fields
   + cost"; the plan's byte-exact response shape won — see DECISIONS.)
