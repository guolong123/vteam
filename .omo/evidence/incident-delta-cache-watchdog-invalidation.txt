2. DESIGN DECISION — (b) rejected as UNSOUND, (a) chosen
--------------------------------------------------------------------------------
(b) "put taskId in the cache key" is unsound. Proof from code:
  - delta/task.completed payloads are both `{...ctx, ...}` from the SAME ctx built per
    execute invocation (worker/src/exec/exec-server.ts:1538-1547; deltas spread it at
    :1877-1881) ⇒ within a turn they agree. That part is fine.
  - BUT the taskId is empty for the very case the bug lives in (team direct chat / DM):
      server/src/chat/worker-dispatcher.ts:2744   taskId: request.taskContext?.taskId ?? '',
      server/src/chat/worker-dispatcher.ts:1907-1909 ...(taskIdForDispatch ? { taskContext: { taskId: taskIdForDispatch } } : {}),
      (taskIdForDispatch = input.taskId, :1868 — set only for the task/execution kind)
    ⇒ for a direct-chat retry the delta payload's taskId is `''` on EVERY turn, so the
    key would be identical across turns ⇒ ZERO cross-turn isolation exactly where D1/D2 live.
  - and for task-driven turns the taskId is per-dispatch data that a follow-up message can
    legitimately reuse ⇒ no guaranteed isolation either.
  ⇒ (b) does not eliminate the class; it only narrows it. REJECTED.

(a) chosen: one public method on WorkerEventIngress + one call from the point that
    actually terminalises the row. Smaller (8 lines in dispatcher, 34 in ingress incl.
    doc) and complete for this path.
    Placement decision: the call is UNCONDITIONAL inside `if (cleanupChannel)` (not inside
    `if (staleIds.length > 0)`) so the invariant is local — "every dispatch in this
    channel starts with a cold streaming cache". When there are no stale rows the delete
    is an idempotent no-op; the only cost in a mid-stream race is one findFirst re-read.
    partDeltaChains is deliberately NOT invalidated: it self-cleans on every chain-tail
    settle (worker-event.ingress.ts:823-827) and deleting a key while a delta task is
    in flight would re-open the findFirst→create check-then-act race the map exists to
    close (this corrects the overstated "partDeltaChains has the same lifecycle gap"
    note in the D1 evidence file — raw proof:
      private runPartDeltaExclusive<T>(...)
        ... void tail.then(() => { if (this.partDeltaChains.get(key) === tail) {
        this.partDeltaChains.delete(key); } });
    ).

8. SETTLING THE (c) CLAIM — session.updated{failed} ordering / crash-between-sends window
--------------------------------------------------------------------------------
Ordering IS guaranteed by construction. worker/src/client/event-client.ts:97-121 —
`send()` awaits its own delivery (`const task = this.deliver(event); ... await task;`,
deliver = POST /worker/events with exponential-backoff retries), and the failure catch
does two sequential awaited sends:
  worker/src/exec/exec-server.ts:1606-1613  AGENT_STATUS{status:'error', error}   (first)
  worker/src/exec/exec-server.ts:1614-1621  SESSION_UPDATED{status:'failed'}       (second)
⇒ agent.status{error} is fully delivered (POST returned ok, or retries exhausted) before
session.updated{failed} is even issued; seq is monotonic per event and eventId unique.

Crash BETWEEN the two sends (agent.status{error} delivered, session.updated{failed} lost):
does it leave an uncovered cache window?  NO. Because the event that matters for the cache
is the FIRST one:
  - agent.status{error} is what drives WorkerDispatcher.handleAgentStatus →
    failTeamProcessingMessage (worker-dispatcher.ts:3409-3417) → row m_A → failed;
  - the same event runs the D1 invalidation (handleAgentStatus, :466-482) → cache entry gone.
So the row is terminalised AND the cache is invalidated by the very event that survived.
The only residue is a Session row left `running`, which is exactly what the idle-dead
watchdog is built to clean (markSessionIdleDead requires status === running, :4740) — and
the D2 hook now invalidates the cache on that path's retry dispatch too.
The reverse inversion (session.updated{failed} arriving first) is equally harmless: it has
no cache effect, and agent.status{error} still invalidates when it arrives. A cache
invalidation keyed on session.updated would have been order-sensitive; keying on
agent.status{error} is not — which is why D1 hooked the agent.status event.

9. RESIDUAL RISKS
--------------------------------------------------------------------------------
- None newly introduced by D2 beyond the D1 notes. The unconditional per-dispatch delete
  can delete a key mid-stream in the (rare) case of two concurrent turns for the same
  channel+agent; the effect is one findFirst re-read on the next delta, not a correctness
  change (documented at the call site).
- If a future caller adds a third row-terminalising path in WorkerDispatcher, they must
  call this.ingress.invalidateDeltaStream(<target channel>, <agentId>) there too; the
  docstring on the method states the invariant.
- Server restart / 256-key FIFO eviction remain the last-resort bounds (unchanged from D1).
