## Approach: pure SQL (no helper script)

Chosen because the target values are a one-shot snapshot of the lane-A constants, and the
row predicate is expressible as a key-order-insensitive JSON comparison. A Node/ts helper
was evaluated and rejected: it would need `ts-node` + `@prisma/client` at deploy time
(the compose runner image ships only compiled `dist/`), whereas the pure-SQL migration is
applied by `prisma migrate deploy` on every fresh deploy and every existing install, and
is self-contained in the SQL runner.

The exact target literals were GENERATED from the uncommitted constants via
`resolveConstantPolicySource(role)` (the same function `seed.ts` mirrors), not hand-typed.
A later `diff` regeneration confirmed the file still byte-matches the current constants
(no drift from concurrent lane edits) — see "Anti-drift re-derivation" below.

## The backfill predicate (exact)

Per built-in id (7): `ep_product, ep_architect, ep_developer, ep_tester,
ep_project_manager, ep_plan, ep_librarian`:

```sql
WHERE id = '<id>'
  AND (
    NOT (JSON_EXTRACT(config, '$.tools')      <=> CAST('<target tools>' AS JSON))
    OR
    NOT (JSON_EXTRACT(config, '$.permission') <=> CAST('<target permission>' AS JSON))
  )
```

`<=>` is MySQL's NULL-safe equal; for two JSON values it compares semantically and is
key-order insensitive (verified: reordered object `{"a":1,"b":2}` <=> `{"b":2,"a":1}` = 1;
nested `edit` map reordered = 1). `JSON_SET(config, '$.tools', …, '$.permission', …)`
rewrites ONLY those two fields, preserving `correction`/`description`/any other config key.
The UPDATE only fires when at least one of the two fields already differs — so a re-run
matches 0 rows. The WHERE also pins the 7 built-in ids exactly, so the user-authored
`ep_0000000001` (and any other custom row) can never be matched.
