F2 FIX — make the question_confirm self-approval check effective for platform questions
=========================================================================================
Plan: .omo/plans/server-gate-removal-tool-authority.md (Final-Verification-Wave fix)
Base HEAD: 30febde (132 suites / 3070 tests green)
Scope: ONLY the F2 blocking finding + its stated re-review conditions. Non-blocking F2

--------------------------------------------------------------------------------
1. BEFORE — the bug (independently confirmed)
--------------------------------------------------------------------------------
`createForPlatform` (questions.service.ts:~621) stored:
    sessionId = (await this.mainAgentSessionOf(taskId)) ?? 's_placeholder'
    agentId   = options.agentId
and recorded the requester's instance id NOWHERE.

`confirmByAgent` (questions.service.ts:313-328) inferred the requester as:
    row.sessionId -> Session.teamMemberId  ==  input.instanceId ?

For a PLATFORM question, row.sessionId is the MAIN member's session (or a
placeholder that misses `session.findUnique` entirely). So the check could never
fire for a non-main requester, and fail-opened completely when there was no
mainAgentMemberId ('s_placeholder' -> findUnique miss).

Live grant check (verified): vteam-product.toolAllows holds BOTH
vteam_team_add_member AND vteam_question_confirm (same for vteam-project_manager).

EXPLOIT (before fix): a non-main vteam-product instance calls team_add_member
(records no requester) -> question_confirm on its own requestId -> the self-check
resolves the "requester" to the MAIN member, never matches the caller ->
resolvePlatformQuestion runs the onResolved hook -> handleTeamAddResolved ->
the agent is added with confirmedBy: '主 Agent' and NO user confirmation.

--------------------------------------------------------------------------------
2. AFTER — the fix (data-integrity, no role gate, no schema change)
--------------------------------------------------------------------------------
(a) createForPlatform now records the true requester in the existing content JSON
    (`content.requesterInstanceId`), threaded from a new optional option
    `options.requesterInstanceId`. No Prisma schema/migration change.

    content = { questions:[...], source:'platform', requesterInstanceId: <string|null> }

(b) teamAddMember (platform-mcp.service.ts) passes `requesterInstanceId:
    args.selfInstanceId`. That identity is already validated by assertWorkerTask
    (anti-impersonation), so it is the trustworthy requester.

(c) confirmByAgent integrity check 1 now reads the recorded requester FIRST:
      - check 1a: recordedRequester === input.instanceId -> 403
        QUESTION_SELF_CONFIRMATION_FORBIDDEN  (works for ANY requester, main or not)
      - check 1b (fallback): when there is NO recorded requester (non-platform
        question, or a legacy/platform row created before this fix), fall back to
        the existing session.teamMemberId comparison. Legacy/absent requester is
        handled DELIBERATELY (documented in the confirmByAgent docblock): the old
        weaker semantics are preserved, NOT silently widened.
    The CROSS_TASK_FORBIDDEN check is unchanged and always in force.

    This is a DATA-INTEGRITY check, not a role/identity gate: authority still comes
    from the agent's own tool allowlist; no mainAgentMemberId- or role-name-based
    permission check was introduced; NO capability was removed (any granted role can
    still confirm OTHER members' requests — proven by the m_B test below).

(d) Stale docblocks corrected (they documented a 403 gate that no longer exists):
      - resolveTeamMainMemberId  (~2853): removed "调用方保持今日 403"; now states it
        no longer acts as an identity gate and no caller 403s on it.
      - taskCreate               (~2880): removed "门 = mainAgentMemberId 解析出的
        主成员 === 调用方 / 否则 403"; now states authority = role toolAllows +
        resolveExecContext anti-impersonation.
      - skillCreate              (~2943): removed "双上下文主门（对齐 task_create）
        … 否则 403"; now states authority = role toolAllows.
      - teamAddMember            (~3807): already correct (no 403 claim) — verified;
        updated to note ANY granted role may raise it and requester is recorded.
    Question text + log de-hardcoded from "主 Agent 申请…":
      QUESTION: "申请将 X（别名 Y）加入团队，是否确认？"  /  "申请将 X 加入团队，是否确认？"
      LOG:      "[team-add] 成员 <selfInstanceId> 申请增员 task=… agent=… requestId=…"

(e) Dead code dropped: server/prisma/seed.ts:70
      `const ROLE_SERVER_GATED_TOOLS: readonly string[] = [] as const;`
    Verified ZERO reads in that file (grep). The separately-exported constant in
    src/common/constants/agent.constants.ts is a DIFFERENT symbol, still referenced
    by specs, and was left untouched.

7. WHAT WAS NOT FIXED (stated plainly)
--------------------------------------------------------------------------------
- Legacy/platform rows created BEFORE this fix carry no content.requesterInstanceId;
  for those, check 1a does not arm and check 1b (session-based) is the only guard,
  so a non-main requester of a legacy platform row can still self-confirm
  (fail-open) until that row is gone. This is documented in the confirmByAgent
  docblock and is the deliberate "do not silently widen" choice. New rows are
  always armed.
- Out-of-scope F2 non-blocking findings (migration drift lock, matrix-spec
  tautology, writeEvidence dirtying the worktree) were NOT addressed.
- The handleTeamAddResolved audited label still says '主 Agent' for agent actors
  (tasks.service message "（经主 Agent 申请、…确认）"). Left as-is: it is an audit
  label, not part of §2, and changing it would ripple into tasks.service/spec
  assertions beyond this fix's minimal-diff mandate.

--------------------------------------------------------------------------------
8. OWNER-DECISION NUANCE (stated explicitly, per task §6)
--------------------------------------------------------------------------------
.omo/drafts/chat-flow-deblocking.md D10 accepted "a product/PM instance could
confirm its own request" as residual risk AFTER the server gate was removed; the
PLAN then mandated integrity checks as the replacement. This fix makes the
mandated check actually function for platform questions. It is strictly safer and
removes no capability (the m_B test proves other members can still confirm). It is
implemented rather than skipped; the D10 tension is recorded here for the owner.
