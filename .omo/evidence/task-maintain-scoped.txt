线上实测：点单个团队的「整理记忆」按钮，返回 `{teams:3, candidates:{...,untags:31}}`
——一次点击捎带整轮全局派发。用户要「点谁整理谁」。

2. 服务端：范围收窄点（只有「团队迭代查询」一处）
====================================================================
`teamsWithActiveMemories(scopeTeamId?)`：

    teamId: scopeTeamId ?? { not: null }     // 全局变体查询**逐字不变**

逐团队管线（candidates → 灰色 system 条 → dispatch internal:true）完全未动，
只是迭代到的团队变少；`summary.teams += 1` 仍只统计**真正派发**的团队（无候选 /
无主 Agent / 无频道的团队不计入）——语义未变。
`runOnce` 的 `lastRunAt` / `running` 冷却态与范围无关，仍每轮更新。

### 定时路径未被污染（关键约束）
`handleFire` 仍是 `await this.runOnce()`（**零参** = 全局变体），scope 只有一个入口：
`POST /memories/maintain` 的 body。env / guard / dedupKey / 排期逻辑一行未动。
新增回归断言：从 `triggers.registerHandler` 取回真实 handler 并调用，
断言 groupBy where 为 `teamId: { not: null }` 且 3 个团队都派发（不继承 scope）。

3. 控制器：house pattern 取舍
====================================================================
团队存在性校验照抄 `src/teams/team-channel-bindings.controller.ts:137-146`
（`team.findUnique({where:{id}, select:{id:true}})` + `NotFoundException
{code:'TEAM_NOT_FOUND', message:'team X not found'}`）——本仓既有的团队 404 惯例，
而不是另造一个错误码。AdminGuard **保留**（范围收窄不放宽鉴权：整理会变更团队记忆）。
空 body：`@Body() dto?` + `dto?.teamId`（body-parser 在无 body 时给 `{}`/undefined，
两条都归一到全局；`whitelist:true`/`forbidNonWhitelisted:false` 下 `{teamId}` 放行）。

web 侧 `api.post(path, undefined)` 经 `lib/api.ts:92` 的
`body !== undefined ? JSON.stringify(body) : undefined` → **不带 body**，兼容空 body 契约。
