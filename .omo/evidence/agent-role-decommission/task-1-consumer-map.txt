Source expression (verified): server/src/chat/worker-dispatcher.ts:2141-2148

Consumed at :2167 `...(resolvedAgentName ? { agent: resolvedAgentName } : {})`.

Three sources can name "which opencode agent runs":
  (1) TeamMember.agentId -> Agent row -> Agent.agentKey -> policy candidate
      `vteam-<agentKey>`;
  (2) TeamMember.opencodeAgentName (per-member explicit override, incl. third-
      party external agents);
  (3) the engine default (neither applies).

THE 4 RULES (normative — both plans cite this statement):
  Rule 1. If a policy candidate resolves (agentKey present and valid) AND the
          worker advertises support for it (workerSupportsAgentPolicies) ->
          the POLICY CANDIDATE WINS; opencodeAgentName is ignored for this
          dispatch.
  Rule 2. Else if TeamMember.opencodeAgentName is set -> IT WINS (covers
          external agents and the gate-off case).
  Rule 3. Else -> OMIT the `agent` key (engine default).
  Rule 4. Post-`role`-removal fallback: resolvePolicyAgentCandidate currently
          falls back to roleToAgentName(role) at :155. With `role` gone, an
          agent with NO agentKey has NO policy candidate -> rules 2/3 apply
          directly. The removal NARROWS the candidate set (no more role-derived
          `vteam-<role>` name); that narrowing must NOT silently change any
          currently-working seeded member -> todo 9's BEFORE/AFTER proof catches
          it. No semantics beyond this narrowing change.

  "(1) 策略候选优先（worker 支持时）→ (2) opencodeAgentName → (3) 引擎默认"
citing this todo. The declaration above MATCHES it.

SECTION 7 — CREATE / CLONE CAPABILITY REPLACEMENT (3 paths, decided)
--------------------------------------------------------------------------------
Today (create): `resolveTemplateSource(tx, dto.role)` looks up `ep_<role>` by id,
then falls back to `resolveConstantPolicySource('vteam-'+role)`; else the
deny-by-default skeleton. Clone is identical except it first deep-copies the
source's bound policy config.

The `AgentRole` entity (plan 2) offers ONLY `key/name/description/type/
defaultAgentId/rolePrompt/sortOrder` — it carries NO capability. Therefore the
capability for a new agent MUST come from one of:

  PATH 1 — explicit `policyId` supplied by the caller
           -> bind it as-is (deep-copied into a new custom policy by
              provisionCustomPolicy), exactly as `create()` does today at :196-205.
           Precedence: HIGHEST (an explicit policy always wins).

  PATH 2 — no `policyId`, but a chosen `AgentRole`
           -> read `AgentRole.defaultAgentId` (the role's default Agent), take
              THAT Agent's `policyId`, and deep-copy its ExecutionPolicy config as
              the new custom policy. This mirrors today's `dto.role` branch but
              sources the template from real Agent/AgentRole data instead of the
              `ep_<role>` id convention.
              `AgentRole.defaultAgentId` is nullable (agent-roles.service
              validates existence, allows null) and may point to a template Agent
              whose policyId is the builtin `ep_<key>`.
           -> if the role has no defaultAgentId, or the default Agent has no
              policyId, fall through to PATH 3.

  PATH 3 — neither `policyId` nor a usable `AgentRole` default
           -> `buildSkeletonConfig` (deny-by-default: edit:* deny, bash deny,
              task deny, tools {}) — unchanged, `create()` :199 / `clone()` :267.

Clone: unchanged shape — deep-copy the SOURCE's bound policy config; if the source
has no policy, apply PATH 2/3 on the clone's target role (source.role is gone, so
"target role" is the explicit policyId, or the chosen AgentRole, or skeleton).

What `create()`'s `role: dto.role ?? null` (agents.service.ts:211) becomes:
  REMOVED. The column is dropped (todo 7). `create()` no longer writes `role`.
  The `ep_<role>` lookup in `resolveTemplateSource` is replaced by PATH 1/2/3.

What the create-form picker (plan 1's `CreateAgentModal`) should post instead
(web agents/page.tsx CREATE_ROLE_OPTIONS :419-422, <select> :2448-2461,
handleSubmit :2253-2266, mutation :2934-2942 — todo 4 owns this):
  - the picker selects an `AgentRole` (id) OR an explicit `policyId`;
  - the payload carries `policyId?: string` and/or `agentRoleId?: string`;
  - it MUST NOT post a `role` string (the column will not exist; the global
    `whitelist:true` pipe would silently strip it and every new agent would fall
    back to the skeleton — the exact defect plan 1 fixed).

LABEL-vs-POLICY decision (destructive-edit guard — explicit earlier decision):
  Changing ONLY the label MUST NOT auto-re-provision the policy. `update()` must
  never rewrite `policyId` because a user picks a different `AgentRole`. The
  label is identity; the policy is capability; editing one never rewrites the
  other. (Consequence to document in todo 4: a user who changes the label keeps
  the existing policy until they explicitly change it.)

DTO decision (todo 5 owns the field shape; recorded here for agreement):
  server `toAgentDto` returns `role` today (:627, :654) and several DTOs pass it
  through. Recommendation: keep the field NAME `role` as the resolved LABEL
  (`AgentRole.name`) for the seeded data so the rendered labels stay byte-identical
  (todo 5's acceptance), and add `roleId` where the UI needs identity. Do NOT
  silently drop a field the UI needs (todo 5's explicit rule). This todo does not
  change any DTO.
