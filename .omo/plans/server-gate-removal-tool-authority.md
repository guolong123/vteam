# server-gate-removal-tool-authority - Work Plan

## TL;DR (For humans)

**What you'll get:** Agents stop being blocked by the platform's own permission checks. Today the server separately decides "is this agent allowed to create a task / move a task / create an issue / switch plan mode", on top of the agent's own tool permissions — and when the two disagree, work stops. After this plan, the only thing that decides what an agent may call is **the agent's own tool permission**. The server keeps checking only that a state change is legal and that the input is valid. Concretely: a "developer cannot create an issue" block disappears for the roles whose job needs it, and a task/plan can no longer be frozen because the plan's status said so.

**Why this approach:** Two independent locks currently guard the same door. The agent-side lock (the worker guard) is the one you can actually configure per role; the server-side lock duplicates it with hardcoded identity rules that cannot be configured at all. Removing the server-side lock and correcting the agent-side grants gives one configurable source of truth. The three changes must land together: removing the server checks while leaving the "hand this tool to the server to decide" exemption in place would make every agent all-powerful; removing the exemption without granting the tools would lock every agent out.

**What it will NOT do:** It will not touch the collaboration rules — who can notify whom, the no-@ default recipient, the main/non-main prompt split, or reply convergence all stay. It will not let an agent accept or archive a task. It will not let a task be worked after it is completed or archived. It will not let a non-main agent write global memory. It will not change the plan-revision hash check.

**Effort:** Large
**Risk:** High - this edits the same permission artefacts four other plans depend on, inverts a safety default, and touches four copies of one constant. If the grants and the worker passthrough are not changed in the same commit, the outcome is either everyone-allowed or everyone-denied, and both look like "the agent is broken" rather than an obvious test failure.

**Decisions to sanity-check:** (1) role grants follow duty — the coordinating roles get task/plan/team tools, and issue creation goes to the roles whose work needs it; (2) plan-mode and managed-confirmation identity checks are removed too, with self-approval closed by new integrity checks and the residual risk recorded rather than silently accepted; (3) the plan-revision hash check is kept while only the status requirement is dropped, and the plan-role exemption from it is removed; (4) the frozen test baselines are authorized to be regenerated; (5) **the main agent is no longer a capability identity** — whoever holds the tool may act, so a team whose main member is a role that was not granted the coordination tools will not get them (this is the deliberate consequence of moving authority to the agent's own tool permission; a team can change its main member or its grants).

**Enumerated consequence you are accepting (decision 1/D9):** `Team.mainAgentMemberId` remains user-selectable to any team member. After this change, capability follows the ROLE's tool grant, not the main designation. Therefore a main member whose role is developer/architect/tester/librarian/plan will hold none of `task_create`/`task_transition`/`plan_mode`/`plan_complete`/`team_add_member`/`question_confirm`/`skill_create`; and a product main will not hold `plan_complete`/`skill_create`. This is intended (authority = tool permission), not a defect — a task-4 test must pin it so it is a documented behaviour rather than a surprise.

Your next move: run `$start-work server-gate-removal-tool-authority` to execute, or ask for a high-accuracy review first. Full execution detail follows below.

## Scope

### Must have
- The removal targets stop refusing calls: `task_create`, `skill_create`, `team_add_member`, `plan_mode`, `plan_complete`, `task_transition`'s main-only check, and `question_confirm` — **7 gated tools across 11 throw sites** (task_create ×2, skill_create ×3, plan_complete ×2, the rest ×1). Each is located by its exact error code, never by line number.
- The plan-status dispatch requirement is gone on both layers, while the plan-revision hash check survives as an independent check.
- Agent authority is expressed by the agent's own tool permission: `SERVER_GATED_SET` stops exempting the gated tools from `mcpDenies`, the worker guard's server-gated passthrough is removed, and each formerly-gated tool is granted explicitly per role.
- The four source copies of the gating constant and the worker passthrough agree on the new value, and the compiled `dist/` artefact is rebuilt.
- Existing DB policy rows are backfilled — `config.tools` AND `config.permission` — so the runtime actually serves the new allowlists (the DB config wins over the constants).
- The `question_confirm` self-approval and cross-task confirmation gaps opened by removing its identity gate are closed with two explicit integrity checks (confirmer ≠ requester; the request belongs to the caller's task).
- The main-designation consequence is pinned by a test: capability follows the role grant, so a team whose main member's role lacks a tool does not get it (the deliberate result of moving authority to the agent's own tool permission).
- The `serverGated` API field and the read-only UI rows it drives are retired, since no tool is server-gated any more.
- The retained server-side checks are enumerated explicitly and proven still enforced: notify routing, terminal-task dispatch refusal, accept/archive refusal (both sites), the global-memory write scope, and the `hook_cancel` owner-or-main rule.
- The frozen permission artifacts are regenerated under an explicit re-baseline authorization, and the gate assertions that encoded the old behaviour are inverted or deleted deliberately.
- An executable role×tool matrix proves the outcome, and two mutation checks prove the tests can actually catch the all-powerful and deny-all failure modes.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No change to the collaboration/routing semantics: `notify_agent` routing (self-notify and non-main→non-main), the group-chat no-@ default recipient, the main/non-main instruction split, and reply-join convergence all stay exactly as they are.
- No change to the terminal-task dispatch rule: execution dispatch into a `completed`/`archived` task is still refused.
- No change to the accept/archive refusal: no agent may accept or archive a task, at either the MCP layer or the service layer.
- No change to the global-memory write scope: writing/updating `global`-level memory still requires the team's main member.
- No removal of the `hook_cancel` owner-or-main check (retained as a resource-ownership rule).
- No removal of the plan-revision hash check, and no exemption from it — only the plan-status requirement is removed.
- No loss of plan-row creation: the `autoEnsureRow` behaviour that the removed status-read plumbing also performed must be preserved or provably replaced.
- No change to the worker's non-gated decision branches: the edit/read globs, `bash` handling, the `task`/`execute` rules, and the unknown-tool fallthrough keep their current semantics apart from the removed server-gated passthrough.
- No new gate, no compensating server-side check, and no A/B dual path or legacy shim for any removed check.
- No change to `Team.mainAgentMemberId` itself (it remains for routing/instruction purposes).
- No re-implementation of the four role plans' work (`AgentRole`, `Agent.role` removal, external-agent display, the permission editor); this plan lands first and they rebase on it.
- No unrequested expansion of any role's capability beyond the grant matrix in this plan.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: **tests-after** + jest (`server`, `worker`) + the three shell e2e scripts + a live-stack role×tool matrix.
- Atomicity proof: todos 2-7 are ONE commit and are exercised together; the tree is required green only at the end of that commit (not after each numbered unit, since the frozen specs are regenerated by its last unit). A test proves an unlisted formerly-gated tool is denied and a granted one is allowed.
- Ordering proof: the commit history must contain NO commit in which the server gates are removed while the `SERVER_GATED_SET` exemption is still live (the all-powerful window). A recorded `git log` check over the flip range asserts the exemption-removal commit is an ancestor-or-equal of the server-gate-removal commit's changeset (i.e. they are the same commit).
- Both-failure-modes proof: two mutation checks are recorded - (a) leaving the `SERVER_GATED_SET` exemption in place while the server checks are removed must make the "no longer all-powerful" test fail; (b) removing the exemption without adding the grants must make the "granted role allowed" test fail.
- Retention proof: every retained server check is asserted still enforced, with its exact error code — routing, terminal-task, accept/archive (both sites), global-memory scope, and `hook_cancel` — plus the two new `question_confirm` integrity checks.
- Baseline proof: the regenerated frozen artifacts are recorded with their new sha, and the full server + worker suites run green in the same change.
- Reference discipline: every gate to remove or keep is identified by its error code or message string; no acceptance criterion may name a line number.
- Evidence: `.omo/evidence/server-gate-removal-tool-authority/task-<N>-server-gate-removal-tool-authority.<ext>`
