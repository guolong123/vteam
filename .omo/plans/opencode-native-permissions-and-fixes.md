# opencode-native-permissions-and-fixes - Work Plan

## TL;DR (For humans)

**What you'll get:** The platform stops running its own permission enforcer and stops re-implementing rules the engine already has. Rules that are expressible in the engine's own configuration stay (so agents are still confined to their task folder); the platform's own tools move their permission check onto the server, where a call without the right permission is refused. Alongside that, three annoyances get fixed: sub-task permission becomes editable, a role can point at an outside agent, and the two glaring dark-mode patches go away.

**Why this approach:** Today there are two home-grown layers guarding the same things — one reimplements the engine's file/command/sub-task rules inside the engine's own process, and one ships our tool permissions as engine config. The engine can express the file/command/sub-task rules natively, so the reimplementation is dead weight; our own tools should be guarded where they actually execute (the server). Deleting the reimplementation is safe only once the server defends our tools, so that lands first.

**What it will NOT do:** It will not lock down or reconfigure the engine's own tools beyond the configuration we already send; it will not change how agents are selected for dispatch; it will not touch the account permission system.

**Effort:** Large
**Risk:** Medium-High - the change reaches into the execution node and deliberately re-baselines a previously frozen artifact; a mistake there silently unprotects the platform's own tools.

**Decisions to sanity-check:** (1) the platform's own tools are refused by the server with a plain "not permitted" error, and the old "you're out of bounds, hand this to X" message disappears; (2) a role's single agent slot can point either at one of our agents or at an outside engine agent, and the per-member outside-agent picker in team detail goes away; (3) the frozen permission baseline is intentionally re-created, because the payload legitimately changes shape.

Your next move: approve, then run `$start-work opencode-native-permissions-and-fixes`. Full execution detail follows below.

## Scope

### Must have
- **Native-only opencode permission.** The emitted per-agent `permission` keeps the keys opencode natively understands (`edit`, `read`, `bash`, `task`, and any other native key we already use) and **drops all `vteam_*` keys**. Verified against opencode 1.18.31's own schema (`https://opencode.ai/config.json`: native `PermissionConfig` = `read, edit, glob, grep, list, bash, task, external_directory, todowrite, question, webfetch, websearch, lsp, skill, doom_loop` + arbitrary tool names; value = `allow|ask|deny` or `{pattern → allow|ask|deny}`).
- **Delete the worker-side interception layer.** `worker/src/role-guard/policy.ts`, `worker/src/role-guard/session-policy-map.ts` (+ specs), the generated plugin `worker/src/resources/role-guard-plugin.ts`, the `<workDir>/.vteam-role-guard/roles.json` injection, and the plugin registration in the injected `opencode.json` all go away. The whole reason this layer exists — guarding `edit`/`write`/`apply_patch`/`bash`/`task`/`browser` — is expressible natively.
- **Sub-task policy is NOT re-implemented.** Rely on opencode's native `task` permission plus native `subagent_depth` (default 1 = "prevents subagents from launching subagents"). If we currently hand-roll "禁套娃", it is deleted, not ported.
- **Server-side enforcement of the platform's own tools.** `vteam_*` tools are still handed to every agent over MCP (unchanged), but a `tools/call` for a tool the caller's bound role does not hold is **refused with 403 + a stable error code**. Allow-list hit → proceed. Explicitly deny / not listed → 403.
- **Issue 1 — `task` becomes editable.** The agents page renders `permission.task` as an editable tri-state (same control style as `bash`), writing through to whatever now owns that value. The read-only badge + explanatory note that made it unchangeable is replaced.
- **Issue 3 — a role binds exactly ONE agent, internal or external, edited in the role editor.** The role editor's single agent selector offers our agents **and** the engine's external agents. The external choice moves out of the team-detail member row.
- **Issue 4 — dark mode.** The role-item active state and the external-agent / member warnings stop using hardcoded light-mode colours; they use the existing dark-aware theme variables.
- **Docs + tests kept true.** `docs/test-cases/08-Agent角色实体化与role拆除.md` is updated for the new behaviour, and the affected e2e specs are updated or replaced.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- **No reduction of the engine's own tool configuration.** `edit`/`read`/`bash`/`task` stay configured exactly as they are (that configuration is how agents stay inside their task folder). Do not "simplify" it away — that would let an agent write anywhere.
- **No new name-based or role-name-based branching** anywhere. No re-introduction of `Agent.role`.
- **No touching the account-permission `Role` / `roles` table** (`schema.prisma` top, `@@map("roles")`) — unrelated RBAC.
- **No change to agent dispatch/selection precedence** (policy candidate → per-member explicit name → engine default) beyond removing the member-level external picker required by issue 3.
- **No A/B dual path, no legacy shim, no "deprecated" annotation.** The removed layer is deleted, not parked.
- **No `ask`-based flow for our own tools.** Headless sessions cannot answer prompts (that is why `bash` is set to `allow`); our refusal is a hard 403, not a prompt.
- **No weakening of the ownership/flow checks** already in `platform-mcp` (worker↔team↔task binding, DM endpoint checks) — the new permission check is additive.
- **No unrelated UI restyling.** Issue 4 is scoped to the specific hardcoded-light spots, not a theme overhaul.
- **No push** until the user says so.
