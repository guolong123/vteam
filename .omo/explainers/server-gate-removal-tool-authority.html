把"能不能做"的决定权，
从平台还给 Agent 自己

现在同一件事有两道锁：一道在 Agent 自己的工具权限上，另一道在平台服务端硬编码的身份规则里。 两道锁经常不一致，结果就是 Agent 被莫名卡住。这份文档说明"做完之后"你会看到什么。

一句话做完之后最直观的三件事

如果你只想记住三件事，看这里就够。

1开发能建 issue 了

现在开发/架构/计划员想开 issue 会被挡；做完后，只要角色的工具权限里有这项，就能开。产品、测试、项目经理本来就能。

2不再被"计划状态"冻住

现在计划没被人工点"开始执行"之前，谁都不能派活。做完后这个状态门取消，只在计划版本对不上时才拦。

3权限只有一处可配

以前要改两次（平台代码 + 角色权限）且经常只改一处。做完后只有一处：角色自己的工具权限表。

现状两道锁锁同一扇门

这是问题的根源，也是"难用"的来源。

现状：锁 ① 与锁 ② 互相独立，经常判出不同结果
⚠ 最要命的不是"有门禁"，而是这两道锁没有一个统一的事实来源

你在角色权限里给某个 Agent 开了权限，它仍然可能被服务端硬编码的规则拒绝； 反过来，某个 Agent 明明不具备某项职责，只要它刚好是团队主 Agent，反而能操作。 排查时看哪个都不对。

使用场景四个真实卡点，前后对照

这些是"功能很难用"最常见的四个具体场景。

开发-1要为一个发现的技术债开 issue
现状

开发在写代码时发现一个必须记录的问题，调用开 issue 的工具 —— 被 Agent 自身工具权限拒绝， 因为"开发"角色的权限表里根本没有这一项。

【越界拦截｜角色：vteam-developer】不能调用 vteam_issue_create。 职责：编码与实现说明…。请把该工作转交 vteam-product， 或使用 vteam_notify_agent 定向通知。

结果是：开发必须先"通知主 Agent"，由主 Agent 代开。为一个 issue 绕一圈。

做完之后

开发的工具权限表里补上了 issue_create，直接开 issue，一次调用完成。

✅ issue 已创建（status: open） 创建者: 开发-1 指派给: 开发-1

这是净新增能力（紫色格），由本次授权表显式决定。

任意 Agent计划还没被人工确认，想派活
现状

计划产出了、也评审完了，但人类还没点"定稿 → 确认执行"。此时派发执行工作： 消息不落库、目标不被唤醒，看起来就像"什么都没发生"。

triggered: false reason: plan-gated hint: 计划未放行：当前计划状态为 pending_final （需 executing，请确认开始执行后再派发）
做完之后

计划状态不再是派发的前提条件。派发正常进行；只有当有人基于旧版计划派活时才会被拦。

✅ 派发成功（triggered: true） 计划 hash 校验保留：若携带的版本与冻结版不符 → 仍会拒绝，并同时给出期望/实际哈希

保留的哈希校验防的是"拿旧计划干活"，与"计划有没有被确认"是两回事。

测试-1想流转任务状态，但它不是主 Agent
现状

任务的推进需要流转状态，但只有主 Agent 能做。其它成员即便发现了阻塞，也无法推进。

403 TASK_STATUS_MAIN_AGENT_ONLY 仅主 Agent（tmm_0000000001）可流转任务状态
做完之后

能否流转由角色工具权限决定。产品经理与项目经理持有该工具，可直接流转； 非法状态流转（如从未开始直接跳到已完成）仍然被拒绝。

✅ 状态已从 pending → in_progress （状态机合法性校验保留：非法迁移返回 409）
整个团队"一个个被阻塞"
现状

三个原因叠加：

  • 计划状态未到 executing → 全体无法派活
  • 非主成员之间不能直接通知（必须经主 Agent 中转）
  • 同团队任务 FIFO 串行，一次只跑一个

观感就是"Agent 一个个卡住，推不动"。

做完之后

第 1 条解除（计划状态门取消）。第 2、3 条保留 —— 它们不是权限，是协作协议：

  • 通知路由保留：防 @ 风暴与 ping-pong 失控
  • FIFO 串行保留：同团队任务排队是设计，不是缺陷

配上第 1 条的解除，团队在计划阶段就能正常推进，不再整体停摆。

不变继续保留的规则（不是权限门）

这些不是"某个 Agent 的身份检查"，而是流程规则、人为授权与资源归属。它们继续生效。

✓任务终态保护

任务已 completed / archived 后，不能往里面派执行工作。防止产生脏数据。

✓验收 / 归档只能人来点

任何 Agent 都不能验收或归档任务 —— 这是人对交付物的确认权，不是 Agent 的能力。

✓通知路由

不能通知自己；成员之间不直接互相派发，经主 Agent 中转。防 @ 风暴。

✓全局记忆写入范围

写"全队/全局"级记忆仍限主 Agent —— 这是共享资源的写入范围，不是能力。

✓计划版本（哈希）校验

只拆"计划状态"门，保留"计划版本对不上就拒绝"。防基于旧版计划执行。

✓流程状态机合法性

状态流转是否合法、参数是否合规、终态是否可改 —— 服务端继续校验。

取舍你需要知道并接受的几条

这些是"权限即 Agent 自身工具权限"的必然结果，不是隐藏的意外。

① 主 Agent 不再是"能力身份"

权限跟角色走，不再跟"谁是主"走。团队的主成员仍然决定 默认收信人等协作行为，但它不再自动获得任务/计划/团队工具。 若某团队的主成员恰好是"开发""架构""测试"或"资料员"，它将不再能建任务、流转任务。

应对方式：换主成员，或给该角色加权限。这是本次设计有意为之的后果，会被测试固化下来。

② 计划模式 / 托管确认的身份门也一并拆除

拆掉后有两点残留风险，已用新增校验兜住：
· 非主成员调用"计划模式"时，改写的仍是团队主成员的执行配置；
· "托管确认"新增两条完整性校验：确认者不能是自己发起的请求，且 请求必须属于自己所在的任务，堵住自我审批与跨任务确认。

③ 这次不动的两个节流/锁

通知节流（3 次/60 秒）与 issue 锁（同执行人重复派发去重）本次保留 —— 它们属于防失控与幂等，不是 Agent 身份权限。如果实测下来仍然影响使用，可以另外单独立项。

更大的蓝图角色 / Agent / 能力：三层分离

上面几节讲的是"权限"这一层。但"角色"这个词现在同时扛着四件不相干的事 —— 这是更底层的混乱来源， 也是它必须跟"权限下放"一起想清楚的原因。

问题：一个"角色"词，扛了四件事

它承担的具体表现本该属于
给人看的标签 "产品经理""开发者"这些展示名称 角色 · 岗位
能做什么 该不该能建任务 / 开 issue / 跑命令 Agent 的能力
提示词内容 "你是谁""你的边界在哪"整段文字 角色 + Agent 各一半
引擎侧的身份 vteam-plan、a_plan 这类硬编码名字 应该消失
⚠ 后果

改一段岗位描述，可能顺手改掉了它的能力；改能力，又可能影响一堆按名字写的特判。 于是系统里长出一批"只有叫这个名字的 Agent 才能做这件事"的硬编码 —— vteam-plan、a_plan、按中文子串匹配角色… 本次计划拆掉了其中一部分（权限层），但角色这个词本身还没有被剥离。

目标：三层各归各位

目标形态：角色（岗位）→ 绑定 Agent → Agent 挂载能力

为什么"文档"组里三个不能合并

它们的真实写范围并不相同：产品经理能写 prototypes，架构师只能写 docs， 测试还要写 tests。若合并成一个 Agent，等于把三者的写范围取并集 —— 架构师就能写 prototypes 和 tests 了，这是扩权。所以： Agent 仍是 7 个（能力各自准确），只是列表按 5 组显示。
