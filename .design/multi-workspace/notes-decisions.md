## 0. 先说根源：为什么会冒出这 4 个问题

这 4 个问题不是 4 件独立的事，而是**同一个根源的 4 个切面**：

> **当前系统是按「一个团队 / 一个组织内部署，所有资源全平台只有一份」设计的；
> 现在要改成「每个用户一份」，于是每一类资源都必须重新回答一次：
> 它到底算「平台共有的」还是「这个用户私有的」？**

仓库里的设计文档当初把这件事写得非常明确，是**有意不做**，不是漏做：

| 出处 | 原文 |
|---|---|
| `docs/agent-platform/01-背景与目标.md:63` | 「**不做多租户 SaaS**（第一版）。平台先以团队内部署形态落地，多租户、计费、跨组织隔离等留待后续迭代」 |
| `docs/agent-platform/29-团队化改造需求说明.md:124` | 「**首版团队为全平台可见，不做按项目隔离**」 |
| `docs/agent-platform/02-用户与场景.md:15` | 「平台采用『**仅团队**』的组织模型：用户归属团队，在团队内以成员身份参与任务」 |
| `docs/agent-platform/37-成员与群聊解耦设计.md:35/44/49/54` | 「成员是**平台级**一等公民」「成员库是**全局资源**」「**一个成员在全局只有一条会话**，跨群/跨任务共享同一上下文」「**跨群记忆是有意为之**，不做技术隔离」 |
| `server/prisma/seed.ts:894` | 「**项目维度已拆除**（remove-project-dimension）」——连更早的「项目」隔离维度都被主动删掉了 |

所以现状是：全平台**一套**模型目录、**一个** worker 节点池、**一个**成员库、团队**全平台可见且名字全平台唯一**、一个成员**一条全局会话**。
你想要的「每个用户拥有自己的工作空间，工作空间内模型 / worker / 成员 / 团队都隔离」，等于要把上面这些「一套」全部拆成「一人一套」。

**这 4 个问题，正好对应你原话里点名的 4 类资源**：

| 你点名的资源 | 对应决策 | 要回答的核心问题 |
|---|---|---|
| 团队 | **空间与成员** | 「空间」这个新框怎么套在现有「账号 / 团队」上？谁和谁算同一个空间？ |
| 模型 | **平台内置资源 + 凭据** | 模型目录（配置）要不要一人一份？里面的 **API key**（密钥）呢？ |
| 成员 | **会话与记忆** | 现在「一个成员全局一条会话、跨群共享记忆」是有意设计，隔离后还成不成立？ |
| worker | **worker 归属**（补充） | 执行任务的算力是大家共用一个池子，还是每个空间独占节点？ |

下面逐个展开。

## 空间与成员：一个用户一个 workspace，还是可进多个 / 可共享？

### 现状
- 账号是**平台内置、全局唯一**的（`User.username @unique`，`schema.prisma:44`）。现在只有 3 个账号：admin / seed-admin / seed-member。
- 「谁能看哪些数据」目前唯一的机制是 **`team_user_members` 表**：用户被加进某个团队，就能看这个团队的全部任务 / 群聊 / 产出物（建团队时自动给创建者落一行 owner）。
- 也就是说，现有共享单位是「**团队**」，不是「用户」。**根本没有「工作空间」这一层概念**。

### 冲突点
「每个用户拥有自己的工作空间」这句话有两种理解，做出来的东西完全不同：

| | 理解 A：一人一空间（且不可共享） | 理解 B：一人可进多空间、空间可加成员 |
|---|---|---|
| 数据模型 | `User` 上加 `workspaceId` 即可，最简单 | 必须新增 `Workspace` + `WorkspaceMember` 两张表 |
| 登录 | 登录后空间固定，前端不需要切换器 | 需要「当前空间」概念 + 顶栏切换器 + JWT 带当前空间 |
| 和现有团队的关系 | 空间 ≈ 用户，团队变成空间内的私有物 | 空间是最外层边界，团队仍是空间**内部**的细粒度共享（现有 `team_user_members` 可保留） |
| 典型场景 | 个人版：每人自己玩自己的 | 团队版：一个部门一个空间，空间内多人协作，还能把外部同事邀请进来 |

### 选错会怎样
- 选了 A，将来要加「邀请同事进我的空间」时，得把 `User.workspaceId` 推倒重做成关联表，是一次数据迁移。
- 选了 B，一开始就要多写两张表、前端多一套切换逻辑，成本高一点，但 A 是 B 的退化情况。

### 建议
**按 B 设计（一人可进多个、空间可加成员）**，因为它是 A 的超集，且能直接复用现有的 `team_user_members`「团队内共享」语义，不用推翻团队模型。如果产品确定永远不共享，落地时把成员表限制成「一个空间只有一个用户」即可。

## 平台内置资源：全局模板是「每空间一份」还是「只读共享」？

### 现状
这些现在是**平台出厂配置，全平台一份**，seed 预置、全局唯一键：

| 资源 | 现状 | 证据 |
|---|---|---|
| 5 个 Agent 角色模板（产品经理 / 架构师 / 开发者…） | 平台级，`type=template` 只读 | `README.md:19-20`、`AgentRole.key @unique` |
| 技能 Skill / 工具 Tool / 执行策略 | 全局唯一名 / action | `Skill.name @unique`、`Tool.action @unique` |
| 模型目录 Model | **全平台 44 个模型，谁都看同一份** | 实证：两个新用户 `GET /models` 都是 total=44 |
| McpServer / GitRepo | 全局表，无 owner | `schema.prisma:1104`、`:1069` |

### 冲突点
你明确说了「工作空间内**包含了模型**……都是隔离的」。但「模型」这个词在这里其实混了两种不同的东西：

1. **模型目录条目**（`providerID + modelID + baseUrl + 是否启用`）——一份**配置**，本身不敏感；
2. **内置模板**（Agent 角色、技能、工具）——平台出厂就有的**公共资产**，理论上每个新用户都该有。

如果两个空间完全各存一份：
- 好处：绝对隔离，一个用户删了「架构师」模板不影响别人；
- 代价：新用户注册时要给 TA 复制一整套模板；以后平台升级（比如新增一个内置角色、修一个内置技能），要逐个空间同步，否则老空间永远用旧版。

如果做成「系统级只读共享 + 空间内可覆盖」：
- 好处：模板统一升级、无冗余；用户想改就复制一份到自己的空间里改；
- 代价：唯一键要改造（内置行 `workspaceId=NULL`，用户自建行带 `workspaceId`），MySQL 没有部分索引，得用生成列 `scopeKey` 实现「NULL 行全局唯一、非 NULL 行空间内唯一」，schema 改动稍复杂。

### 选错会怎样
- 全私有：将来「平台统一升级内置模板」会变成运营噩梦。
- 全共享：用户改了内置模板会影响所有空间，等于没隔离（而且 `.unique` 全局撞名问题还在）。

### 建议
**模板类（Agent 角色 / 技能 / 工具 / 执行策略）用「系统级只读 + 空间内覆盖」；模型目录按你要求做成空间内可见/可配**。但注意：**模型凭据不是配置，见「凭据」一节，必须私有**。

## 凭据：模型 API key / git 私钥 / webhook secret / MCP oauth 是否必须按空间私有？

### 现状（这是最危险的一处，和「平台内置资源」完全不同）
这些不是「配置」，是**密钥**，而现在全平台**共用一份**：

| 凭据 | 现状 | 证据 |
|---|---|---|
| 模型 provider token | `ModelCredential @@unique([providerID])` —— **一个 provider 全平台只有一行**，注释写「token 全局 provider 粒度（关键决策①）」 | `schema.prisma:1018-1032` |
| 下发方式 | 保存任一 provider 的 key → **全表解密** → 广播到**全部在线 worker** → 写进每个 worker **单份** `auth.json` | `models.service.ts:1641-1672`、`workers.service.ts:705-714` |
| git 私钥 | 所有用户所有仓库的明文 key 打包写进**同一个** `.keta-git-creds.json` | `worker/src/git/git-credential-injector.ts:21,63-78` |
| 渠道 / MCP 密钥 | `MessageChannel.secrets`、`NotificationChannel.secrets`、`McpServer.oauth.clientSecret` 全是全局表、无归属 | `schema.prisma:1351/1388/1111` |

**实测含义**：A 用户配置/吊销自己的 `openai` key，B 用户的模型立刻一起失效；A 录入的 git 私钥，B 的 Agent 也能拿去用；任何登录用户都能读到别人的 webhook secret。

### 冲突点
「平台内置资源」里「模板能不能共享」是个**产品体验/运维成本**取舍；「凭据」是**安全红线**，没有中间地带：

- 共享一份 = 任何一个用户都能看到、改到、吊销别人的密钥（凭据泄露 + 互相破坏）；
- 每空间一份 = 需要改唯一键 `@@unique([workspaceId, providerID])`，并且凭据下发链路要从「全表广播」改成「按空间过滤 + 只下发该空间 worker」。`notes-runtime.md` D3/E6 给出了具体改法。

### 选错会怎样
允许共享 = 多用户上线即等于**把 A 的 API key 交给 B**，这是能直接造成资损/数据泄露的事故级问题，且事后无法靠权限点补救（因为权限点只判「能不能改」，不判「改的是谁的」）。

### 建议
**必须 per-workspace，没有商量余地**。这也是我在 `README.md` 里把它列为 P0-2 的原因。「平台内置资源」的共享只适用于不含密钥的模板/配置，凭据类的密钥一律私有——这两条不矛盾，务必分开看。

## 会话与记忆：设计文档 37 篇的「全局会话 + 跨群共享记忆」是否要为空间隔离反转？

### 现状（这条最反直觉，需要多解释）
2026-11 的「成员与群聊解耦」改造（37 篇 / `.design/member-decouple/`）做了一次**产品明确决策**，把会话模型整个改了：

> `docs/agent-platform/37-成员与群聊解耦设计.md:35`：
> 「同一个成员在**全局只有一条会话（Session）**，跨群 / 跨任务**共享同一上下文**，群聊 / 私聊 / 任务只是这条会话的『轮次上下文』」

配套决策：
- **D4**（`:44`）：「配置共享、会话全局：一个成员在全局只有一条 Session（`member_key = member_id` 唯一），跨群、跨任务共享同一上下文……**这是本方案与旧设计最大的偏离**」
- **D14**（`:54`）：「**跨群记忆是有意为之**：接受 A 群上下文可能出现在 B 群……**不做技术隔离**。这是 D4 的直接代价；技术隔离等于回到会话隔离，与决策矛盾」
- **D9**（`:49`）：「成员库是**全局资源**」；`Member.name @unique`（成员名全平台唯一，@ 寻址用）
- 落地代码：`Session.memberKey? @unique`（`schema.prisma:423`），`SESSION_SCOPE=member` 时启用（默认还是旧的 `seat` 按席位隔离，`session-scope.ts`）

**翻译成人话**：平台的「数字员工」是全局唯一的，比如全平台只有一个叫「架构师-老周」的成员，它同时服务 A 群和 B 群，而且**它记得 A 群聊过什么，会把这份记忆带到 B 群**。这是产品**特意要的**效果，文档里明说「跨群记忆是目标而非禁区」。

### 冲突点
现在要把「成员」也隔离到工作空间里，就会正面撞上这个决策：

- 如果 A 空间和 B 空间**各自都有一个叫「架构师-老周」的成员**（这是「成员隔离」最自然的理解），那它们还能共用同一条会话吗？
  - 共用 → A 空间的聊天内容、任务上下文、记忆会流到 B 空间，**等于空间隔离白做了**（而且比数据列表泄露更隐蔽：是混进模型 prompt 里的）。
  - 不共用 → 必须把 `Session.memberKey` 唯一键从「全局 `member_id`」改成「`(workspaceId, member_id)`」，也就是**推翻 37 篇 D4/D14 的产品决策**，连「一成员一条会话」「跨群记忆」的运行时语义、私聊单频道（`uk_channels_dm(member_id)`）、`Memory.level='global'` 自动注入都要重写。
- 另外 `Memory` 表里还有 `level='global'` 的**显式无归属全局记忆**，`autoInject` 会把它注入主 Agent 的 prompt（`schema.prisma:1266-1276`），多用户下 A 的全局记忆会进 B 的 prompt——同一个问题。

### 选错会怎样
这一条**不是加个字段能糊过去的**：如果只给 Member/Session 加 `workspaceId` 列、但不改「一成员一条全局会话」的语义，隔离就是假的（数据层看着隔离了，运行时上下文还在串）。所以必须先由产品明确「跨群/跨空间共享记忆」这个特性还要不要，再决定运行时怎么改。

### 建议
**默认反转：改成「一空间内一成员一条会话」，全局记忆降为「空间内全局」**。理由：你要的是「工作空间内信息都隔离」，而共享记忆是跨边界的信息流动，与隔离目标直接冲突。如果产品确实想保留「同一数字员工跨空间携带记忆」，那就得把它定义成**显式的、用户可感知的共享能力**（而不是默认行为），并且单独做隔离豁免设计——这会显著增加复杂度，建议单独评审。

> 补充：这个开关目前是**进程级全局环境变量** `SESSION_SCOPE`（`session-scope.ts:10-16`），不是按用户/空间切换的。租户化后它要么下线，要么变成空间内配置，对应 `README.md` 里的「会话作用域灰度开关」。

## worker：节点是「平台共享池」还是「按空间归属」？

> 这条你上一轮也点名了「worker 要隔离」，虽然不在「最关键的 4 个」里，但背景一并交代。

### 现状
- compose 里就**一个** worker 容器（`w_compose_worker`），全平台所有任务都派给它（`workers.service.ts:1001-1004` 按 `status != offline` 从全平台候选池挑）。
- 全平台共用**一枚** `WORKER_TOKEN`（`worker-token.guard.ts`），`GET /workers/register-token` 普通 member 都能拿到明文。
- 模型凭据、git 凭据、MCP 配置都是**按 worker 单份**下发/注入（`auth.json`、`opencode.json`、`.keta-git-creds.json` 各一份）。

### 冲突点
「worker 隔离」有两种做法，成本差很多：

| | 方案 A：每空间独占节点 | 方案 B：共享池 + 每会话强隔离 |
|---|---|---|
| 做法 | `Worker` 加 `workspaceId`，派任务只在本空间节点里挑，凭据只下发本空间节点 | 仍共用一个 worker，但每个会话携带 `workspaceId + 会话票据`，worker 侧按空间起多份隔离域 / 多份 auth.json |
| 隔离强度 | 强（连磁盘、进程、密钥都物理分开） | 依赖票据与代码纪律，共享进程内的任何疏漏都会串 |
| 成本 | 每个用户/空间都要起一套 worker 容器，资源占用线性增长；小空间也占一个空节点 | 省资源，但 `notes-runtime.md` 的 P0-7/P0-8（MCP 误归属、事件回流串会话）正是共享池下才会触发的 |
| 现有风险 | — | 不改的话，两个空间的任务跑在同一个 worker 上，MCP 会按「该 worker 最近会话」把 A 的调用归属到 B 的任务（代码 `:8439-8440` 自承） |

### 建议
**起步用方案 A**（严格隔离，最省心、也最容易证明「真的隔离了」），等用户规模上来、确实需要省资源时再评估 B。无论哪种，都必须把 `WORKER_TOKEN` 从「全平台一枚」改成 per-worker 密钥，并给事件 / MCP 请求带上空间身份。

## 一张总表：你点名的 4 类资源，改造后各归谁

| 资源 | 当前 | 目标（建议） | 依赖决策 |
|---|---|---|---|
| 账号 | 全局唯一、3 个预置账号 | 账号仍可全局唯一，但归属到「空间成员关系」 | 空间与成员 |
| 团队 | 全平台可见、名字全平台唯一 | 空间内可见、`@@unique([workspaceId, name])` | 空间与成员 |
| 模型目录 | 全平台 44 个一份 | 空间内可见/可配 | 平台内置资源 |
| **模型凭据（key）** | **全平台一份** | **每空间一份，绝不共享** | **凭据（安全红线）** |
| 成员 | 全局成员库、名字全局唯一 | 空间内成员库；会话/记忆改为空间内 | 会话与记忆 |
| 会话 / 记忆 | 一成员一条全局会话、跨群共享记忆 | 一空间内一成员一条；全局记忆降为空间内 | 会话与记忆 |
| worker 节点 | 全平台一个池、一枚共享 token | 每空间独占节点（起步） | worker 归属 |

## 由总原则推导的三分类（后续所有改造的判定依据）

判据：**「这行数据是不是某个用户创建/配置的」**。

- **平台资源（D6 后归属 `ws_system`，所有人可读只读）**：平台内置 Agent 模板、AgentRole 岗位模板、Skill、Tool、ExecutionPolicy、**Model 模型目录条目**、内置 McpServer。其唯一键**统一改为 `(workspaceId, ...)`**，内置行的 `workspaceId` 固定为 `ws_system`（不再「保持全局唯一」）。
- **必须 per-workspace**：Team / TeamMember / TeamQueue / TeamUserMember、Member、Session / SessionTurn、ChatChannel / Message / MessageReceipt、Task / TaskEvent、Artifact / ArtifactVersion、Issue / IssueActivity、Plan / PlanTask、Memory、AgentQuestion、**ModelCredential / GitCredential / GitRepo / GitRepoGrant / 用户自建 McpServer / MessageChannel / NotificationChannel / 各绑定表 / ExternalUser**、Worker / WorkerModelAvailability / TaskGroupInstance、RealtimeEvent、Trigger / Hook、ModelUsage、uploads/workdir 文件、SSE 订阅。
- **系统级本体（自身不隔离，承载归属）**：User、Role、Workspace、WorkspaceMember。账号仍全局唯一，多空间归属靠 `WorkspaceMember`（**不是**每空间独立账号）。

⚠️ 最容易判错的两处：
1. **Agent / Skill / Tool / Model 目录是「模板/目录」→ 全局**；但用户**克隆出来的 Agent 实例**、**填的 provider key**、**录入的 git 仓库 / 自建 MCP / 渠道**是用户态 → 必须私有。
2. 「跨群共享记忆」不是被删除，而是**被限定在「同一个空间内的多个群」之间**；**跨空间绝不互通**。这正是用户第 4 条「成员服务多个群也需要按空间隔离」的含义。

# 附录二：「用户自建 Agent / MCP 与内置模板共存」的答复与统一建模（2026-11-12）

**问题**：`agents` 一张表同时装「平台内置模板」和「用户自建/克隆行」，`workspaceId` 该不该加？加了内置行怎么办？唯一键 `agentKey @unique` 全局唯一会让两个空间撞名。

**用户答复（原话）**：「用户创建的就是所属于用户啊，加一个空间概念，默认系统的空间是一个特殊的空间，所有人都拥有，然后用户创建的属于他所属的空间就好了吧。」

**定稿**——这是比原方案更简洁的统一模型，**取消了「部分表不加 workspaceId」的例外**：

| 项 | 结论 |
|---|---|
| 所有资源表 | **统一 `workspaceId NOT NULL`**，唯一键统一 `@@unique([workspaceId, ...])` |
| 系统空间 | `Workspace` 中一行 `ws_system`（`isSystem=true`），**所有人隐式拥有**（不落成员行），承载所有 seed / 平台内置数据；普通用户只读，管理员可维护，不可删除 |
| 用户空间 | 用户（或管理员）在某个空间里创建的一切都归该空间 |
| 读语义 | 平台资源类模型：`workspaceId IN (当前空间, 'ws_system')`；用户态模型：严格 `= 当前空间` |
| 写语义 | 一律 `= 当前空间`；写 `ws_system` 仅平台管理员走专门入口 |

**统一建模如何解决这个问题**：
- `agents` 表：模板行 `workspaceId='ws_system'`（`type='template'` 天然可区分），用户克隆/自建行归其当前空间 ⇒ 同表共存，`agentKey` 改 `@@unique([workspaceId, agentKey])` 后**跨空间可同名**。
- `mcp_servers` 表：内置 `vteam`/`vteam-api` 归 `ws_system`，用户自建归当前空间 ⇒ **不需要新增 `isBuiltin` 列**，用 `workspaceId` 就能区分。
- `Skill` / `Tool` / `AgentRole` / `ExecutionPolicy` / `Model` 目录同理：seed 行归 `ws_system`，管理员在空间内新建的行归该空间。

**为什么这比原方案（部分表加列、部分表整表豁免）更好**：
1. 消除例外清单，schema 与中间件逻辑单一；
2. 不需要 `workspaceId` 可空 + 生成列 `scopeKey`（MySQL 无 partial index）的补丁；
3. 内置行与用户行的唯一键冲突问题一并消失；
4. 语义清晰：**「平台提供的」和「你创建的」在同一套模型里用 `workspaceId` 区分**。

# 附录三：平台管理员跨空间读取与资源空间迁移（2026-11-12）

**用户答复原文**：「3 能，且需要能够有权限修改资源的空间，某些场景下可能需要让一个 worker 或者模型能够给多个空间使用，在这个时候可以修改资源的空间为系统默认空间。其它都按建议。」

**定稿要点**：

| 事项 | 结论 |
|---|---|
| 平台管理员跨空间读 | **允许**（读任意空间；写仍限当前空间）。前端给管理员「查看其他空间」入口，明确标注跨空间只读 |
| 修改资源的空间 | **新增受控能力**：独立审计端点（不是通用 PATCH），默认仅平台管理员，可通过权限点授予运维账号 |
| 共享 worker / 模型 | 做法就是**把资源迁移到 `ws_system`**：迁移后所有空间可读，可共享类型同时可「使用」（Worker 进入共享候选池、模型/凭据对所有空间可用） |
| 回收共享 | 从 `ws_system` 移出，需先做依赖检查；仍被其它空间引用则拒绝并返回引用清单 |
| 迁移白名单 | 只允许「配置/能力类」：Agent、角色、技能、工具、执行策略、模型目录、模型凭据、MCP、Git 仓库+凭据、Worker；**团队 / 任务 / 会话 / 成员 / 消息 / 产出物等业务数据不允许迁移**（迁移会破坏语义） |
| 共享 worker 的凭据边界 | 共享节点**只用系统空间凭据**；私有凭据任务只能派到本空间节点，找不到就明确报错 |
| 安全权衡 | 共享 = 主动放弃隔离；必须二次确认 + 审计 + UI 标识 + 可回收；凭据类共享默认禁用 |

**影响**：`WorkspaceGuard` 对管理员读操作放行；新增 `platform.view_all_workspaces` 与 `platform.relocate_resource` 权限点；新增审计表（原 `audit_logs` 是预留未建）；M2 增加迁移端点与副作用重放；M3 增加管理员跨空间入口与「移动到空间 / 共享到平台」交互；测试矩阵新增 5 条相关场景。
