# 4.10 通知与 IM 集成（需求设计说明）

## 模块概述

任务执行是异步的，状态变化需要主动触达相关人员。本模块解决"任务结果与审批待办如何通知到人"的问题：通过出站 Webhook 对接外部系统，通过企业微信机器人推送任务结果摘要与审批待办卡片，并预留飞书 / 钉钉等多渠道适配能力。通知与 IM 是"人工在环"闭环的最后一公里，审批卡片直达让审批人不需要进入平台即可发起决策。

本模块与 4.5 Task（状态变更事件来源）、4.6 审批（审批待办与 TTL 提醒）、4.4 Flow（触发配置）、4.8 插件（企业微信插件）联动；通知订阅与 4.5 的 Webhook 触发共用同一套事件模型，入向（触发）与出向（通知）两条链路对称设计。

## 需求列表

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-1001 | 任务状态变更（完成 / 失败 / 等待审批）通过**出站 Webhook** 通知外部系统 | P1 |
| FR-1002 | 支持**企业微信**机器人通知：任务结果摘要、审批待办卡片（点卡片跳转审批） | P1 |
| FR-1003 | 预留飞书 / 钉钉等 IM 的通知适配能力（同一消息模板引擎，多渠道渲染） | P2 |
| FR-1004 | 支持从 IM 发起任务 / 触发流程（企业微信指令触发） | P2 |

## 详细设计说明

### 通知事件与订阅模型（FR-1001）

平台内部统一的事件总线模型，通知基于事件订阅，事件与 4.5 的入站 Webhook 共享同一套 `traceId` 语义：

| 事件 | 触发时机 | 通知内容示例 |
|---|---|---|
| task.succeeded | 任务成功终态 | 任务摘要、耗时、Token 成本 |
| task.failed | 任务失败终态 | 失败节点、错误分类、Trace 链接 |
| task.waiting-approval | 进入等待审批 | 审批卡片（见 FR-1002） |
| approval.expired | 审批 TTL 到期 | 过期提醒 / 升级通知 |
| task.paused / resumed / cancelled | 生命周期干预 | 状态变更摘要 |

通知订阅声明为资源，按命名空间隔离：

```yaml
apiVersion: orchestra.io/v1alpha1
kind: NotificationRule
metadata:
  name: notify-ops-group
  namespace: dev-team
spec:
  events:                          # 订阅哪些事件
    - task.succeeded
    - task.failed
    - task.waiting-approval
  channels:                        # 投递到哪些渠道
    - type: webhook
      url: https://ops.example.com/hooks/orchestra
      secretRef: notify-webhook-secret     # 出站签名 Secret（4.1 Secret 加密存储）
      retry: { maxRetries: 5, backoff: exponential }
    - type: wecom
      robotId: wecom-robot-ops
  template: notify-default         # 可覆盖命名空间级模板（FR-1003）
  enabled: true
```

设计要点：

- 事件负载为 JSON，统一包含 `traceId`、`taskRef`、`namespace`、`event`、`timestamp`，接收方可通过 API 拉取详情。
- 投递失败按退避策略重试（默认 5 次指数退避），重试耗尽后进入投递失败告警，绝不静默丢弃。
- 通知规则可随时启停，不影响任务执行本身（通知是旁路，失败不阻断流程）。

### 出站 Webhook 安全（FR-1001 / NFR-01）

- 出站请求携带签名头（HMAC-SHA256，基于 Secret 与请求体），接收方校验防伪造。
- 请求体不包含任何凭证明文；任务输出摘要截断（默认 1KB），完整内容走 API 按权限拉取。
- 出站目标域名校验：禁止投递到内网 / 云元数据地址（SSRF 防护，NFR-01），与入站请求同规则。

### 企业微信机器人通知（FR-1002）

- 企业微信插件提供机器人能力（见 4.8 `settings` 集成分组的机器人配置），通知策略可配置：哪些事件、投给哪个机器人 / 群。
- 审批待办卡片结构：

```
┌──────────────────────────────┐
│ ⏳ 待审批：需求文档评审       │
│ 流程：软件公司开发流程 v3     │
│ 提交人：Agent 需求分析        │
│ 检查点：review-gate（第 2 轮）│
│ TTL：剩余 23 小时            │
│ [查看并审批] ──深链跳转──▶   │
└──────────────────────────────┘
```

- 卡片跳转链接指向平台 Web 控制台的审批详情页（`#approval-detail` 深链），控制台地址在全局设置配置。
- 审批完成后推送结果反馈（批准 / 驳回 / 打回摘要），形成闭环。
- 企业微信发送凭据走 4.1 Secret 加密存储，按命名空间隔离（与 4.8 插件凭证规则一致）。

### 统一消息模板引擎（FR-1003）

- 通知内容由模板引擎渲染：模板按事件类型定义，变量注入（任务名、节点、审批人、链接、耗时、成本等）。
- 多渠道仅差异渲染：同一模板数据渲染为企业微信卡片 / 飞书卡片 / 钉钉卡片，正文语义一致。
- 新增 IM 渠道 = 新增渲染适配器，不改事件源与模板逻辑，符合 NFR-08 标准协议优先原则。
- 模板支持命名空间级覆盖（品牌 / 语气 / 附加字段），覆盖优先级：命名空间模板 > 平台默认模板。

### IM 发起任务（FR-1004）

- 企业微信指令触发：群内发送指令（如 `@机器人 发起需求分析 #issue-42`），机器人解析参数，校验权限后调用与 4.5 Webhook 同源的创建任务接口。
- 指令触发与 Webhook 共用幂等键设计（来源类型 + 消息 ID，如 `wecom:msg-xxxx`），重复指令不产生重复任务（NFR-04）。
- 指令权限遵循命名空间 RBAC：发起人需具备 task-initiator 角色，越权指令返回明确错误提示并写入审计。
- 指令支持参数化输入透传（如 `issueNumber=42`），与 4.5 的 `input` 参数化能力打通。
- IM 触发为 P2，M3 落地；M1 / M2 以 Webhook 与出站通知为主。

### 与原型的关系

- `settings` 全局设置：集成分组的企业微信插件卡片与通知配置入口，展示通知渠道的启停与连接状态。
- `trigger-manage` 触发器配置：定时与 Webhook 双 tab 提供事件入口的可视化配置，与通知订阅共用事件模型。
- `approval` 审批中心：企业微信待办卡片的深链落地页，卡片与平台列表数据同源。

## 验收要点

- 配置出站 Webhook 后，任务成功与失败均收到结构化通知，负载含签名头且不含凭证明文。
- 进入等待审批时企业微信收到待办卡片，点击可直达审批详情页完成决策，决策后收到结果反馈。
- 通知投递失败按退避策略重试，重试耗尽后进入告警，不静默丢失。
- 新增飞书渠道时复用同一模板引擎，仅新增渲染适配器，事件源与模板无改动。
- 企业微信指令触发任务时校验发起人权限，越权指令被拒绝并返回原因；重复指令只创建一个任务。
